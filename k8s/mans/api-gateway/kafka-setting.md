# Золотой стандарт конфигурации надежности (Production-ready сетап) для Apache Kafka на уровне инфраструктуры, продюсера и консьюмера.


## Шаг 1. Надежность на уровне Инфраструктуры (k8s/kafka.yaml)
На реальном продакшене (где запущено минимум 3 ноды Кафки) критически важно, чтобы сообщения дублировались. Для этого топик создается с несколькими копиями (репликами).
Добавьте эти параметры в env: вашего kafka.yaml (для продакшена значения меняются на 3, но для Minikube мы фиксируем их на безопасную единицу, чтобы одна нода не падала):

```yaml
          env:
            # Количество синхронных копий топика, необходимых для подтверждения записи
            - name: KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR
              value: "1" # (На проде: "3")
            - name: KAFKA_OFFSETS_TOPIC_MIN_ISR
              value: "1" # (На проде: "2" — запись успешна, только если подтвердили 2 ноды из 3)
            # Автоматическое создание топиков (лучше выключить, чтобы контролировать структуру)
            - name: KAFKA_AUTO_CREATE_TOPICS_ENABLE
              value: "false"

```

## Шаг 2. Надежность на уровне Продюсера (tasks-service)
Задача продюсера — гарантировать, что отправленное сообщение точно долетело до диска Кафки и не потерялось в сети.
Добавьте эти параметры в application.yml вашего tasks-service:

```yaml
spring:
  kafka:
    producer:
      # 1. Подтверждение записи (all или -1)
      # Брокер ответит Java-приложению только тогда, когда ВСЕ реплики запишут сообщение на диск.
      # Это гарантирует нулевую потерю данных (Zero Data Loss).
      acks: all
      
      # 2. Повторные попытки при сетевых сбоях
      # Если сеть моргнет, Spring будет автоматически пытаться отправить сообщение снова
      retries: 5
      
      # 3. Защита от дубликатов (Идемпотентность)
      # Если сообщение долетело до Кафки, но ответ сети потерялся, продюсер отправит его снова.
      # Этот флаг гарантирует, что Кафка отфильтрует дубликат и сохранит сообщение строго ОДИН раз.
      properties:
        enable.idempotence: "true"
        max.in.flight.requests.per.connection: 5 # Оптимальное число для идемпотентности
```

## Шаг 3. Надежность на уровне Консьюмера (users-service, notifications-service)
Задача консьюмера — гарантировать, что если в процессе обработки сообщения (например, при отправке уведомления) микросервис внезапно упадет или отключится электричество, сообщение не потеряется и будет обработано заново после перезапуска.
По умолчанию Spring автоматически подтверждает прочтение (enable-auto-commit: true) каждые 5 секунд. Это опасно: Spring может подтвердить Кафке, что всё ок, а через секунду ваша Java упадет со сбоем, и сообщение пропадет навсегда.
Переходим на ручное подтверждение (Manual Ack):

```yaml
spring:
  kafka:
    consumer:
      # Отключаем автоматическое подтверждение
      enable-auto-commit: false
      # Читаем топик с самого начала при первом запуске группы
      auto-offset-reset: earliest
    
    # Включаем ручной режим подтверждения (Manual Immediate)
    # Теперь Кафка передвинет указатель только тогда, когда наш Java-код сам скажет: "Я всё обработал!"
    listener:
      ack-mode: manual_immediate
```

## Как теперь должен выглядеть ваш Java-код Листенера:
Чтобы ручное подтверждение работало, в метод @KafkaListener нужно просто добавить один параметр — Acknowledgment acknowledgment, и вызвать его в самом конце метода:

```java
@KafkaListener(
        topics = "tasks-topic",
        groupId = "users-group"
)public void consumeTaskEvent(TaskEvent event, Acknowledgment acknowledgment) {
    try {
        log.info("🚀 Обработка сообщения из Кафки: {}", event.getTaskId());
        
        // Тут ваша бизнес-логика (запись в БД, логика и т.д.)
        
        // СТРОГО В САМОМ КОНЦЕ: Если код дошел сюда без ошибок,
        // мы вежливо говорим Кафке: "Я всё успешно сделал, сдвигай указатель!"
        acknowledgment.acknowledge(); 
        
    } catch (Exception e) {
        log.error("Ошибка при обработке сообщения. Указатель НЕ сдвигается, попробуем позже: ", e);
        // Мы НЕ вызываем acknowledgment.acknowledge(). 
        // При следующем перезапуске под снова получит это сообщение и попытается обработать его еще раз.
    }
}

```

## Итог: Что дает этот паттерн?
Этот шаблон конфигурации обеспечивает гарантию доставки класса At-Least-Once (Минимум один раз).

   1. Продюсер защищен от дубликатов и требует 100% подтверждения записи от кластера.
   2. Консьюмер никогда не потеряет сообщение «на лету»: если в блоке try вылетит ошибка, сообщение останется в Кафке и дождется исправления кода или перезапуска системы.

Вы проделали грандиозный путь и теперь полностью контролируете всю цепочку микросервисов, баз данных, Istio и Kafka. Сохраните эти манифесты и настройки — это ваш личный эталонный золотой стандарт. # Надежность отправки сообщений

Да, этот код концептуально соответствует настройке ack-mode: manual_immediate, но в нем есть одна очень важная ловушка, из-за которой поведение системы может отличаться от ваших ожиданий (особенно в блоке catch).
Давайте разберем подробно, как это работает на самом деле в Spring Boot, и где кроется подвох.

## Что здесь работает правильно?
В секции try всё отлично. При настройке manual_immediate, как только ваш код вызывает acknowledgment.acknowledge(), Spring Kafka моментально отправляет запрос на брокер для фиксации (коммита) этого смещения (offset). Указатель сдвигается, сообщение считается успешно обработанным.

## В чем заключается ловушка (блок catch)?
В вашем комментарии написано: «При следующем перезапуске под снова получит это сообщение...» — и вот здесь кроется критическая ошибка понимания работы Spring Kafka Container.
Если вы просто поймали Exception, залогировали его и вышли из метода, для Spring Kafka это выглядит так: «Метод @KafkaListener завершился без ошибок».
Даже если вы не вызвали acknowledgment.acknowledge(), цикл poll() консьюмера продолжит читать следующие сообщения из топика в рамках этой же сессии. Сообщение не будет переотправлено вам немедленно, и поток не заблокируется.

Что произойдет на самом деле при вашем коде:

   1. Вы упали в catch, залогировали ошибку и вышли из метода.
   2. Консьюмер берет из буфера следующее сообщение и снова вызывает ваш @KafkaListener.
   3. Если следующее сообщение обработается успешно и вы вызовете acknowledgment.acknowledge(), то Spring закоммитит новый, более дальний offset.
   4. Итог: Упавшее сообщение будет визуально «пропущено» брокером (хотя в БД или логику оно не попало). Но если в этот момент перезапустить приложение (до того, как обработалось следующее успешное сообщение), то да — чтение начнется с упавшего сообщения.


## Как сделать правильно?
В Spring Kafka управление ошибками при ручном коммите должно быть явным. У вас есть три правильных пути в зависимости от бизнес-логики:

## Вариант 1. Использовать @RetryableTopic (Рекомендуется)
Не нужно писать try-catch внутри метода для логирования ошибок. Позвольте исключению вылететь наружу из метода @KafkaListener. Spring сам перехватит его, не закоммитит offset и отправит сообщение в Retry-топик, а после — в DLT.

```java
@RetryableTopic(attempts = "3", backoff = @Backoff(delay = 2000))
@KafkaListener(topics = "my-topic", groupId = "my-group")
public void listen(MyEvent event, Acknowledgment acknowledgment) {
    log.info("Обработка сообщения: {}", event.getTaskId());
    
    // Ваша бизнес-логика (без try-catch)
    orderService.process(event); 
    
    // Коммитим ТОЛЬКО при успехе
    acknowledgment.acknowledge(); 
}

```

## Вариант 2. Если нужно жестко заблокировать поток до исправления (Stop Container)
Если данные критичны и их нельзя пропускать или нарушать порядок, при ошибке нужно принудительно останавливать чтение топика, выбрасывая специальное исключение Exception наружу (опять же, не глотать его в catch), чтобы сработал стандартный DefaultErrorHandler. Он будет пытаться вызвать метод снова или остановит контейнер.

## Вариант 3. Ручной откат (nack) — если нужно повторить именно сейчас
Если вы хотите при ошибке сразу же попробовать обработать это сообщение еще раз (или вернуть его в очередь внутри приложения), вместо пустого catch нужно вызвать nack(...):

```java
try {
    log.info("Обработка сообщения: {}", event.getTaskId());
    orderService.process(event);
    acknowledgment.acknowledge(); // Успех
} catch (Exception e) {
    log.error("Ошибка! Просим Кафку вернуть сообщение на повтор", e);
    // nack(sleepTime) — сбрасывает текущую пачку (poll) 
    // и заставляет консьюмер снова прочитать это упавшее сообщение через 1000 мс
    acknowledgment.nack(Duration.ofMillis(1000)); 
}

```


## Резюме
Ваш код в try идеален для manual_immediate. Но пустой catch без проброса Exception наружу или без вызова acknowledgment.nack(...) приведет к скрытой потере сообщений (они пропустятся при обработке последующих удачных записей).

# Конфиги для applications.yaml

При разработке на Spring Boot (Java) надежность (Reliability) в Apache Kafka складывается из настроек трех компонентов: Продюсера (Producer), Брокера/Топика (Broker/Topic) и Консьюмера (Consumer).
Ниже приведены ключевые параметры конфигурации, которые необходимо задать в application.yml или через Java-конфигурацию KafkaTemplate / ConcurrentKafkaListenerContainerFactory для обеспечения максимальной отказоустойчивости и гарантии доставки сообщений.

## 1. Надежность на стороне Продюсера (Producer)
Эти параметры гарантируют, что отправленное сообщение не потеряется по пути к брокеру.

| Параметр в application.yml | Значение для высокой надежности | Описание |
|---|---|---|
| spring.kafka.producer.acks | all (или -1) | Брокер подтверждает запись только после того, как сообщение сохранено на всех синхронных репликах (ISR). Защищает от потери данных при падении лидера. |
| spring.kafka.producer.properties.enable.idempotence | true | Включает идемпотентность продюсера. Предотвращает дублирование сообщений в сетевых сбоях (автоматически выставляет acks=all, retries=MAX). |
| spring.kafka.producer.retries | 2147483647 (MAX_INT) | Количество попыток переотправки при ошибках. При включенной идемпотентности можно оставлять максимальным, регулируя время через delivery.timeout.ms. |
| spring.kafka.producer.properties.delivery.timeout.ms | 120000 (2 мин) | Максимальное время, в течение которого продюсер будет пытаться доставить сообщение (включая ретраи), прежде чем вернет ошибку. |
| spring.kafka.producer.properties.max.in.flight.requests.per.connection | 1–5 | Если идемпотентность true, можно ставить до 5 (порядок сообщений гарантируется). Если false, то строго 1 для сохранения порядка сообщений. |

## 2. Надежность на стороне Брокера и Топика (Cluster/Topic)
Настройки самого кластера Kafka (задаются при создании топиков, например, через бин NewTopic в Spring).

* replication.factor ≥ 3
Количество копий данных в кластере. Для продакшена стандарт — 3 реплики.
* min.insync.replicas ≥ 2
Минимальное количество реплик (включая лидера), которые должны подтвердить запись, чтобы acks=all считался успешным. Если живых реплик меньше этого числа, продюсер получит ошибку NotEnoughReplicasException.
* unclean.leader.election.enable = false
Запрещает выбирать лидером реплику, которая не входит в состав ISR (In-Sync Replicas). Это исключает потерю данных, но снижает доступность топика в критических сбоях.
 

## 3. Надежность на стороне Консьюмера (Consumer)
Эти параметры определяют, как приложение обрабатывает сообщения и когда сообщает Kafka, что задача успешно выполнена.

| Параметр в application.yml | Значение для высокой надежности | Описание |
|---|---|---|
| spring.kafka.consumer.enable-auto-commit | false | Отключает автоматическую фиксацию смещений (offsets). Смещение должно коммититься только после успешной обработки сообщения кодом приложения. |
| spring.kafka.listener.ack-mode | MANUAL_IMMEDIATE или RECORD | Режим фиксации смещения в Spring. RECORD коммитит после выхода из метода @KafkaListener. MANUAL_IMMEDIATE требует ручного вызова acknowledgment.acknowledge(). |
| spring.kafka.consumer.properties.max.poll.interval.ms | Зависит от бизнес-логики | Максимальное время между вызовами poll(). Если ваш код обрабатывает пачку сообщений дольше этого времени, Kafka посчитает консьюмер «мертвым» и запустит ребалансировку. |
| spring.kafka.consumer.properties.max.poll.records | Умеренное (например, 10–50) | Ограничивает количество записей, возвращаемых за один poll. Помогает уложиться в max.poll.interval.ms при тяжелой обработке. |


## 4. Обработка ошибок в Spring Boot (Retry & DLT)
Для обеспечения отказоустойчивости на уровне бизнес-логики Spring Kafka предоставляет мощные механизмы переотправки и изоляции ошибок: [1] 

   1. Контейнеры повторных попыток (Retries): Начиная со Spring Kafka 2.8+, используются аннотации @RetryableTopic. Если метод @KafkaListener выбрасывает исключение, сообщение автоматически отправляется в специальный retry-топик для повторной обработки через заданный интервал. [1] 
   2. Dead Letter Topic (DLT): Если все попытки обработки завершились неудачей, сообщение перенаправляется в DLT-топик (например, topic-name-dlt) для последующего ручного анализа, а основной поток обработки (Consumer) продолжает читать следующие сообщения, не блокируя систему. [1] 

```java
@RetryableTopic(
    attempts = "3",
    backoff = @Backoff(delay = 2000, multiplier = 2.0),
    topicSuffixingStrategy = TopicSuffixingStrategy.SUFFIX_WITH_INDEX_VALUE
)
@KafkaListener(topics = "orders", groupId = "order-group")public void listen(Order order) {
    // Если здесь упадет Exception, Spring отправит сообщение в retry/DLT топики
    orderService.process(order);
}

```

* Допустима ли семантика At-least-once (хотя бы раз) или строго нужна Exactly-once (ровно один раз)? [2]  


# Отправка сообщений в кафку под транзакцией

Вы затронули одну из самых важных и классических проблем в микросервисной архитектуре — атомарность записи в базу данных и отправки сообщения в брокер (Dual Write Problem).
Если коротко: делать отправку в Kafka напрямую внутри метода сохранения заказа можно, но это несет в себе огромные риски рассинхронизации данных, если не настроить систему правильно.


## В чем главная опасность (Проблема двойной записи)
Представьте стандартный метод сервиса:

@Transactional // Транзакция базы данныхpublic void createOrder(Order order, OrderEvent event) {
    orderRepository.save(order); // 1. Запись в БД
    orderProducerService.sendOrder("orders-topic", order.getId(), event); // 2. Отправка в Kafka
}

Что может пойти не так:

* Сценарий А: Заказ сохранился в БД, сообщение ушло в Кафку, но в самом конце метода (или при коммите транзакции) произошел сбой БД (например, constraint violation или отвалилась сеть). Результат: В БД заказа нет, но консюмеры в Кафке уже получили сообщение и начали его обрабатывать. Данные рассинхронизированы.
* Сценарий Б: Заказ записался в БД. При вызове sendOrder Кафка временно недоступна или упала по таймауту. Метод выбрасывает исключение, транзакция БД откатывается (Rollback). Тут данные консистентны (нигде ничего нет), но пользователь получил ошибку 500, хотя база данных была полностью исправна.


## Как поступить правильно (3 надежных варианта)
В зависимости от требований к надежности и сложности проекта, выберите один из следующих архитектурных подходов.
## Вариант 1. Использование механизма TransactionSynchronization (Самый простой)
Вы можете сказать Spring: «Отправь сообщение в Кафку только ПОСЛЕ того, как транзакция базы данных будет успешно зафиксирована (committed)».

```java
import org.springframework.transaction.annotation.Transactional;import org.springframework.transaction.support.TransactionSynchronization;import org.springframework.transaction.support.TransactionSynchronizationManager;

@Transactionalpublic void createOrder(Order order, OrderEvent event) {
    orderRepository.save(order); // Запись в БД (пока не закоммичена)

    // Регистрируем действие после успешного коммита
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            // Этот код выполнится ТОЛЬКО если БД успешно сохранила данные
            orderProducerService.sendOrder("orders-topic", order.getId(), event);
        }
    });
}

```

* Плюсы: Исключает Сценарий А. Сообщение не уйдет, если база упала.
* Минусы: Если база закоммитилась, но в момент afterCommit упала сама Кафка — сообщение потеряется.


## Вариант 2. Паттерн "Outbox Table" (Самый надежный / Промышленный стандарт)
Вместо отправки в Кафку напрямую, вы сохраняете сообщение в специальную таблицу outbox в той же самой базе данных и в той же самой транзакции.

```java
@Transactionalpublic void createOrder(Order order, OrderEvent event) {
    orderRepository.save(order); // 1. Сохраняем заказ
    
    OutboxMessage outbox = new OutboxMessage("orders-topic", serializeToJson(event));
    outboxRepository.save(outbox); // 2. Сохраняем сообщение в соседнюю таблицу
}

```


Отдельный независимый процесс (например, инструмент [Debezium](https://debezium.io/) через CDC или простой @Scheduled шедулер в Spring) постоянно читает таблицу outbox, отправляет новые строки в Kafka и помечает их как отправленные.

* Плюсы: 100% гарантия атомарности. Если транзакция прошла — данные в безопасности. Кафка может лежать часами, шедулер отправит всё, как только она оживет.
* Минусы: Требуется создание дополнительной таблицы и фонового процесса отправки.


## Вариант 3. Использование Kafka Transactions (Если нужно связать именно цепочку Кафки)
Spring Kafka поддерживает распределенные транзакции (Chained Transaction Managers). Вы можете объединить транзакцию БД и транзакцию Кафки в одну общую с помощью KafkaTransactionManager [Transactional Kafka Producer].

* Плюсы: Из коробки поддерживается Spring.
* Минусы: Настройка распределенных транзакций (2PC) усложняет инфраструктуру, бьет по производительности брокера и не всегда стабильно работает при жестких сетевых сплитах.


## Рекомендация для старта
Если проект учебный или средней нагрузки, начните с Варианта 1 (afterCommit) — это пишется в 5 строк кода и защищает от критического рассинхрона (когда в базе данных нет, а в Кафке есть). Если проект готовится под высокую надежность (Mission Critical), сразу закладывайте Паттерн Outbox (Вариант 2).
Какой из вариантов распределения транзакций вам ближе? Мы можем подробно разобрать код для последовательного коммита (afterCommit) или посмотреть на структуру таблицы для Outbox-паттерна.
