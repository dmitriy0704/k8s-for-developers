# Core DNS

**CoreDNS** — это **DNS-сервер**, который работает внутри кластера Kubernetes и
отвечает за **разрешение имён сервисов** (и других внутренних ресурсов) внутри
кластера.

Простыми словами: это «телефонная книга» Kubernetes. Когда под хочет обратиться
к другому сервису по имени (например, `http://backend:80` или
`postgres.default.svc.cluster.local`), именно CoreDNS превращает это красивое
имя в реальный IP-адрес пода.

### Почему CoreDNS важен

Без DNS внутри кластера пришлось бы везде хардкодить IP-адреса сервисов (а они
меняются при пересоздании подов) — это было бы очень неудобно и ненадёжно.

CoreDNS делает возможным **именной доступ**:

- `my-service` → внутри того же namespace
- `my-service.my-namespace.svc.cluster.local` → полный FQDN
- `my-service.my-namespace` → тоже работает (Kubernetes автоматически
  подставляет текущий namespace)

### Основные функции CoreDNS в Kubernetes

| Функция                          | Что делает простыми словами                                                               |
|----------------------------------|-------------------------------------------------------------------------------------------|
| Разрешает имена сервисов         | Превращает имя сервиса в ClusterIP или IP подов (из EndpointSlice)                        |
| Поддерживает разные типы записей | A (IPv4), AAAA (IPv6), SRV (для портов), PTR (обратный DNS)                               |
| Кэширует ответы                  | Ускоряет повторные запросы (TTL обычно 5–30 секунд)                                       |
| Поддерживает upstream DNS        | Если имя не найдено внутри кластера → пересылает запрос во внешний DNS (например 8.8.8.8) |
| Обслуживает headless-сервисы     | Возвращает сразу все IP подов StatefulSet (для прямого подключения к репликам)            |
| Поддерживает плагины             | Очень гибкий: можно добавить свои правила, метрики, логи, health-check и т.д.             |

### Как CoreDNS устроен в Kubernetes

- Запускается как **Deployment** в namespace `kube-system`.
- Обычно 1–2 реплики (в production рекомендуют 2–3 для отказоустойчивости).
- Service типа **ClusterIP** с именем `kube-dns` (или `coredns`) на порту 53.
- Все поды в кластере получают адреса DNS-серверов через **--cluster-dns** в
  kubelet (обычно 10.96.0.10).

Проверить в кластере:

```bash
kubectl get pods -n kube-system | grep coredns
kubectl get svc -n kube-system kube-dns
```

### Типичный ConfigMap CoreDNS (configmap coredns в kube-system)

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: coredns
  namespace: kube-system
data:
  Corefile: |
    .:53 {
        errors
        health
        kubernetes cluster.local in-addr.arpa ip6.arpa {
           pods insecure
           fallthrough in-addr.arpa ip6.arpa
        }
        prometheus :9153
        forward . /etc/resolv.conf
        cache 30
        loop
        reload
        loadbalance
    }
```

Здесь:

- `kubernetes` плагин — главный, который отвечает за имена сервисов
- `forward` — пересылает внешние запросы (например google.com → 8.8.8.8)
- `cache` — кэширует ответы
- `prometheus` — отдаёт метрики для мониторинга

### Когда CoreDNS может быть проблемой

- Поды в состоянии `CrashLoopBackOff` → часто из-за того, что CoreDNS не может
  стартовать (нет ресурсов, ошибка конфига).
- DNS не резолвится → смотри логи CoreDNS, проверь ConfigMap, убедись, что поды
  получают правильный `--cluster-dns`.
- Высокая нагрузка → добавь реплики или включи `cache` побольше.

### Коротко одним предложением

**CoreDNS** — это встроенный DNS-сервер Kubernetes, который позволяет подам
обращаться друг к другу по красивым именам сервисов (вместо изменчивых IP),
автоматически обновляет записи при изменении подов и пересылает внешние запросы
дальше — без него нормальная работа микросервисов в кластере была бы почти
невозможна.
