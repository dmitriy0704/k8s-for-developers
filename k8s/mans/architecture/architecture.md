# Заметки по изучению Kubernetes

## Архитектура

Система Kubernetes представляет собой слой абстракции, реализующий рабо-
чие нагрузки, поверх таких базовых элементов вычислительной системы, как
виртуальные или реальные машины и балансировщики нагрузки.
Виртуальные(или реальные) машины называются `узлами` (nodes) и объединяются в
кластер (cluster). Один или несколько контейнеров объединяются в так называемый
`под`(Pod), который является в Kubernetes минимальной единицей планирования.
Сетевое взаимодействие определяется с помощью `сервисов` (Service). Такие
высокоуровневые элементы, как `развертывание` (Deployment), позволяют еще
больше упростить работу с подами.

Кластер Kubernetes — это набор узлов, представляющих собой те вычислительные
мощности, на которых запускаются контейнеры. Обычно это виртуальные маши-
ны, однако могут использоваться и чисто аппаратные (невиртуализированные)
машины. На каждом из этих узлов запускается `kubelet` — специальный процесс
системы Kubernetes, который отвечает за взаимодействие с управляющим слоем
(control plane) (процессом системы Kubernetes, осуществляющим оркестрацию)
и управление жизненным циклом контейнеров, запускаемых на узлах с помощью
среды запуска контейнеров.

Внутри кластера один или несколько (при использовании режима высокой
доступности) узлов играют особую роль(`управляющая нода`): они выполняют запуск
самой программы оркестрации Kubernetes (рис 3.2). Эти особые узлы составляют
управляющий слой и отвечают за следующие действия:

- предоставление API, используемого для взаимодействия с кластером с помощью
  различных инструментов, таких как утилита командной строки Kubernetes;
- хранение состояния кластера;
- координацию работы входящих в кластер узлов для выполнения запланированных
  действий над контейнерами (запуска, остановки, повторного запуска).

### Сервис

Поды в Kubernetes — сущности временные. Они постоянно умирают и рождаются
заново (например, при обновлении или сбоях), и каждый раз получают новый
внутренний IP-адрес.
Если ваше клиентское приложение будет обращаться напрямую к IP пода, оно
сломается, как только под перезапустится.
Сервис решает эту проблему: он дает один постоянный IP, который не меняется, и
сам перенаправляет трафик на живые поды.

Главные функции сервиса:

- Service Discovery (Обнаружение): Вам не нужно знать IP подов, достаточно знать
  имя сервиса (например, http://time-service).
- Балансировка нагрузки: Если у вас 3 копии (реплики) пода, сервис будет
  распределять входящие запросы между ними по очереди.
- Абстракция: Сервис «понимает», какие поды к нему относятся, с помощью Labels (
  меток). Если метка пода совпадает с селектором сервиса, трафик пойдет туда.

Аналогия:

Представьте Call-центр.
Поды — это операторы. Они уходят на обед, увольняются и меняются.
Сервис — это единый номер телефона (например, 8-800...).
Клиент звонит на один номер, а система автоматически соединяет его со свободным
оператором. Клиенту не важно, какой именно оператор ответит.

# Основные структурные компоненты Kubernetes

Kubernetes состоит из **кластера**, который делится на две большие части:

- **Control Plane** (управляющая плоскость, «мозг» кластера) — отвечает за
  принятие всех решений, хранение состояния и управление.
- **Worker Nodes** (рабочие узлы) — машины, где реально выполняются твои
  приложения (поды с контейнерами).

Вот основные **структурные компоненты** (на февраль 2026 года архитектура
остаётся почти такой же, как в 2015–2016 годах, с небольшими улучшениями в
реализации и добавлением In-Place Pod Resize и т.п.).

### 1. Control Plane (управляющая плоскость)

Это центральная часть, которая обычно работает на отдельных серверах (в
production — несколько для высокой доступности). В minikube всё собрано в одной
машине/контейнере.

| Компонент                                  | Простыми словами что делает                                                                                                                                                   | Где живёт                            | Обязателен?                   |
|--------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------|-------------------------------|
| **kube-apiserver**                         | Главная точка входа. Принимает все команды (kubectl apply, get, delete и т.д.), проверяет их, сохраняет в etcd и отдаёт ответы.                                               | Control Plane                        | Да, единственный обязательный |
| **etcd**                                   | Распределённая база данных (key-value). Хранит **всё реальное состояние кластера** — какие поды должны быть, сервисы, конфиги, секреты и т.д.                                 | Control Plane (часто 3+ узла для HA) | Да, без него кластер мёртв    |
| **kube-scheduler**                         | «Планировщик». Смотрит на новые поды без узла и решает, на какую ноду их поставить (учитывает CPU, память, affinity, taints, nodeSelector и т.д.).                            | Control Plane                        | Да                            |
| **kube-controller-manager**                | Набор контроллеров в одном процессе. Следит, чтобы реальность соответствовала желаемому состоянию: пересоздаёт упавшие поды, управляет ReplicaSet, Node, Job, Endpoint и т.д. | Control Plane                        | Да                            |
| **cloud-controller-manager** (опционально) | Интеграция с облаком (AWS, GCP, Azure). Управляет LoadBalancer, Node, StorageClass и т.д.                                                                                     | Control Plane (в облаке)             | Только в облаке               |

### 2. Worker Nodes (рабочие узлы)

Это обычные машины (физические, виртуальные, облачные инстансы), где запускаются
твои приложения.

| Компонент             | Простыми словами что делает                                                                                                                   | Где живёт          | Обязателен?                       |
|-----------------------|-----------------------------------------------------------------------------------------------------------------------------------------------|--------------------|-----------------------------------|
| **kubelet**           | «Агент» на каждой ноде. Получает от apiserver список подов → запускает/останавливает контейнеры, следит за их здоровьем, шлёт статус обратно. | Каждый worker node | Да, без него нода не работает     |
| **kube-proxy**        | Сетевой помощник. Настраивает правила балансировки для Service (iptables, IPVS или nftables). Делает ClusterIP, NodePort и т.д.               | Каждый worker node | Да (или заменяется eBPF в Cilium) |
| **Container Runtime** | Программа, которая реально запускает контейнеры (pull образов, создаёт/останавливает).                                                        | Каждый worker node | Да                                |
| **Pod Network (CNI)** | Плагин сети (Calico, Cilium, Flannel, Weave и т.д.). Даёт каждому поду уникальный IP и обеспечивает связь без NAT.                            | Каждый worker node | Да, без него поды не общаются     |

### Краткая схема (как всё связано)

- Ты пишешь `kubectl apply -f deployment.yaml` → запрос идёт в
  **kube-apiserver** → сохраняется в **etcd**.
- **kube-controller-manager** видит изменение → создаёт ReplicaSet.
- **kube-scheduler** находит подходящую ноду → присваивает поду nodeName.
- **kubelet** на этой ноде видит задачу → через **Container Runtime** запускает
  контейнеры.
- **kube-proxy** на всех нодах настраивает сеть для Service.
- **CNI** обеспечивает, чтобы поды общались по IP.

Всё это работает в **цикле примирения** (reconciliation loop): контрольная
плоскость постоянно проверяет «желаемое состояние» (из etcd) против «реального»
и исправляет расхождения.

### Дополнительно (не основные, но часто упоминаются)

- **CoreDNS** — DNS-сервер внутри кластера (для имён сервисов типа
  my-service.default.svc.cluster.local).
- **Metrics Server** — собирает метрики CPU/памяти для HPA.
- **Ingress Controller** / **Gateway Controller** — не часть core, но часто
  устанавливаются для внешнего трафика.

Если коротко одним предложением:  
Kubernetes — это **Control Plane** (принимает решения и хранит состояние) + *
*множество Worker Nodes** (выполняют работу), где главные «рабочие лошадки» — *
*kube-apiserver**, **etcd**, **kubelet** и **kube-proxy**.

# KUBE-APISERVER

**kube-apiserver** — это **самый центральный и важный компонент** всего
Kubernetes.  
Без него кластер фактически не существует.

Простыми словами: это **единственная официальная дверь**, через которую **все**
взаимодействуют с кластером.

### Что именно делает kube-apiserver

| Функция                                | Простыми словами                                                                     |
|----------------------------------------|--------------------------------------------------------------------------------------|
| Принимает все запросы                  | kubectl apply, get, delete, describe, port-forward, logs и т.д. — всё идёт сюда      |
| Проверяет аутентификацию и авторизацию | Кто ты (токен, сертификат, OIDC, webhook и т.д.) и имеешь ли право это делать        |
| Валидирует запросы                     | Соответствует ли манифест схеме, проходят ли валидационные вебхуки, mutating вебхуки |
| Сохраняет/читает состояние             | Всё, что ты создаёшь/меняешь — сохраняется в etcd через kube-apiserver               |
| Отдаёт ответы                          | Возвращает статус, список объектов, события, метаданные                              |
| Обеспечивает watch-механизм            | Клиенты (kubectl, контроллеры) могут подписаться на изменения в реальном времени     |
| Реализует aggregation layer            | Позволяет расширять API кастомными CRD (Custom Resource Definitions)                 |
| Обеспечивает consistency и versioning  | Гарантирует, что все видят одинаковое состояние, поддерживает несколько версий API   |

### Ключевые факты про kube-apiserver (2026 год)

- **Единственная точка записи** — всё, что меняет состояние кластера, проходит
  через него.  
  Ни scheduler, ни controller-manager, ни kubelet **не пишут напрямую в etcd** —
  только через apiserver.

- **Stateless** (почти) — сам по себе не хранит состояние. Всё состояние лежит в
  **etcd**.  
  Можно запускать несколько реплик kube-apiserver (load balancer перед ними) —
  они все читают/пишут в один etcd.

- **Запускается как обычный процесс** (в production обычно в поде в namespace
  kube-system, в HA-кластерах — несколько реплик).

- **Слушает по HTTPS** (порт 6443 по умолчанию) — все клиенты (kubectl,
  клиентские библиотеки, контроллеры) общаются только по TLS.

- **Поддерживает несколько версий API** одновременно  
  Например, apps/v1, apps/v1beta1, networking.k8s.io/v1 — всё это обрабатывает
  один и тот же apiserver.

- **Расширяемость**:
    - Admission controllers (ValidatingWebhook, MutatingWebhook)
    - Aggregation API (чтобы добавлять свои API, например metrics.k8s.io)
    - CustomResourceDefinitions (CRD)

### Типичная схема работы (очень упрощённо)

1. Ты выполняешь `kubectl apply -f deployment.yaml`
2. kubectl → HTTPS запрос на
   kube-apiserver (https://api.example.com:6443/apis/apps/v1/namespaces/default/deployments)
3. kube-apiserver:

- проверяет токен / сертификат
- проверяет RBAC (можешь ли ты создавать Deployment)
- валидирует манифест (соответствует ли схеме)
- применяет mutating вебхуки (если есть)
- сохраняет объект в etcd
- возвращает тебе 201 Created + статус

4. kube-controller-manager видит новый Deployment → создаёт ReplicaSet
5. kube-scheduler видит поды → назначает ноду
6. kubelet запускает поды

Всё это время **kube-apiserver** — единственный, кто напрямую трогает etcd.

### Как посмотреть kube-apiserver в реальном кластере

В minikube (всё в одном контейнере):

```bash
minikube ssh
ps aux | grep kube-apiserver
# или
crictl ps | grep kube-apiserver
```

В production-кластере (kubeadm, kops, EKS и т.д.):

```bash
kubectl get pods -n kube-system | grep apiserver
kubectl logs -n kube-system kube-apiserver-minikube   # или имя пода
```

### Коротко одним предложением

**kube-apiserver** — это **центральный мозг и единственная официальная точка
входа** Kubernetes: он принимает, проверяет, сохраняет и отдаёт все команды и
состояние кластера, а всё остальное (scheduler, контроллеры, kubelet) общается
только с ним.

# ETCD

**etcd** — это **самый важный и критический компонент хранения состояния** в
Kubernetes.  
Без etcd кластер просто не может работать — он теряет всю информацию о том, что
вообще происходит.

Простыми словами: etcd — это **надёжная распределённая база данных**, куда *
*kube-apiserver** записывает **всё желаемое и текущее состояние кластера**, а
все остальные компоненты (контроллеры, scheduler, kubelet) читают оттуда правду.

### Основные характеристики etcd

| Характеристика     | Что это значит простыми словами                                                                  |
|--------------------|--------------------------------------------------------------------------------------------------|
| Тип базы данных    | key-value store (распределённый, с сильной согласованностью)                                     |
| Консистентность    | **Strong consistency** — все узлы видят одинаковые данные в один момент времени (линейнаяizable) |
| Протокол           | gRPC + HTTP/JSON API (но Kubernetes общается через kube-apiserver, а не напрямую)                |
| Хранение данных    | Всё в памяти + на диске (WAL — write-ahead log + snapshots)                                      |
| Размер кластера    | Обычно **3, 5 или 7 узлов** (нечётное количество для кворума)                                    |
| Кворум             | Для записи/чтения нужно большинство узлов (например, 2 из 3 или 3 из 5)                          |
| Производительность | Очень быстрая на чтение/запись (тысячи операций в секунду), но чувствительна к задержкам сети    |
| Размер данных      | В типичном кластере 1–10 ГБ (редко больше 20–30 ГБ даже в очень больших кластерах)               |

### Что именно хранится в etcd

Практически **всё состояние кластера**:

- Все объекты Kubernetes: Pod, Deployment, Service, ConfigMap, Secret,
  Namespace, Role, ClusterRole и т.д.
- Статус объектов (running/pending/terminated)
- Events (события)
- Lease (для leader election контроллеров)
- Custom Resource Definitions (CRD) и их экземпляры
- Настройки кластера (например, feature gates)

etcd хранит **только желаемое состояние** (desired state) и **статус** (status),
который обновляют контроллеры и kubelet.

### Как etcd работает в кластере

- **kube-apiserver** — **единственный**, кто пишет и читает из etcd напрямую.
- Все остальные компоненты (scheduler, controller-manager, kubelet) общаются *
  *только** с apiserver — никогда напрямую с etcd.
- etcd запускается как **распределённый кластер** (raft consensus algorithm):
    - Один лидер (leader election через raft)
    - Остальные follower'ы
    - Лидер принимает все записи, реплицирует на большинство follower'ов
    - Если лидер падает — выбирается новый за секунды

### Почему etcd такой важный и критичный

- **Нет etcd → нет кластера**  
  kube-apiserver не может стартовать, kubectl не работает, ничего не читается/не
  пишется.

- **Потеря данных в etcd** = потеря всего кластера  
  Поэтому в production всегда:
    - 3–7 узлов etcd
    - Регулярные snapshots (автоматически через kubeadm или операторы)
    - Backup (velero, etcdctl snapshot save)
    - Отдельные быстрые SSD-диски (latency критично)

- **Задержки или потеря кворума** → apiserver становится read-only или полностью
  останавливается.

### Как посмотреть etcd в реальном кластере

В minikube (всё в одном поде):

```bash
minikube ssh
crictl ps | grep etcd
# или
journalctl -u etcd   # если systemd
```

В production-кластере (kubeadm, kops, EKS и т.д.):

```bash
kubectl get pods -n kube-system | grep etcd
kubectl logs -n kube-system etcd-minikube
```

### Коротко одним предложением

**etcd** — это **надёжная распределённая база данных**, в которой **хранится всё
состояние Kubernetes**; kube-apiserver пишет туда желаемое состояние, а
контроллеры и kubelet читают и приводят реальность в соответствие — без etcd
кластер мёртв.

Если интересно — могу рассказать подробнее про:

- как делать бэкап и восстановление etcd
- как работает raft consensus в etcd
- почему нельзя подключаться к etcd напрямую (и что будет, если попробовать)
- как мониторить etcd (метрики, алерты)

# KUBE-SCHEDULER

**kube-scheduler** — это один из ключевых компонентов **control plane**
Kubernetes, который отвечает за **размещение подов** по узлам кластера.

Простыми словами: это «умный планировщик», который решает вопрос:  
«На какой ноде (машине) запустить этот новый под, чтобы всё работало оптимально
и не сломалось?»

### Что именно делает kube-scheduler

1. **Смотрит на новые поды**  
   Когда в кластере появляется под **без назначенной ноды** (nodeName пустой),
   scheduler получает уведомление через watch на kube-apiserver.

2. **Фильтрует подходящие ноды** (Filtering / Predicates)  
   Проверяет все ноды кластера и отсеивает те, которые **не подходят** по разным
   причинам.  
   Самые частые фильтры (predicates):

- хватает ли CPU / памяти (NodeResourcesFit)
- соответствует ли nodeSelector / nodeAffinity
- есть ли taints, которые под не терпит (TaintToleration)
- не нарушает ли PodAffinity / AntiAffinity
- нода не в состоянии NotReady / Unschedulable
- под не превышает лимиты ноды (например, max pods per node)

3. **Ранжирует оставшиеся ноды** (Scoring / Priorities)  
   Из тех нод, что прошли фильтры, выбирает **самую лучшую** по баллам.  
   Примеры scoring-функций:

- LeastRequestedPriority — отдаёт предпочтение нодам с наименьшей загрузкой
  CPU/памяти
- BalancedAllocation — старается не перегружать одну ноду
- ImageLocality — предпочитает ноды, где уже есть нужные образы (меньше pull)
- NodeResourcesBalancedAllocation, InterPodAffinity и т.д.

4. **Присваивает ноду поду**  
   Записывает в объект Pod поле `spec.nodeName` → kube-apiserver сохраняет это в
   etcd.  
   Дальше kubelet на выбранной ноде видит задачу и запускает под.

### Важные особенности kube-scheduler

- **Работает только один** активный экземпляр (leader election через lease в
  etcd).  
  Можно запускать несколько реплик, но работает только лидер.

- **Не запускает поды сам** — только **назначает** ноду.  
  Запуск — задача kubelet.

- **Stateless** — не хранит состояние, читает всё из apiserver/etcd.

- **Очень быстрый** — обычно решает за миллисекунды–секунды даже в кластерах с
  тысячами нод.

- **Настраивается**:
    - Плагины фильтрации и scoring (можно отключать/включать, добавлять свои)
    - Профили (несколько scheduler'ов для разных типов нагрузки)
    - Extender (устаревший способ расширения, сейчас лучше плагины)
    - Descheduler (отдельный компонент, который потом может «переселять» поды)

### Как посмотреть kube-scheduler в кластере

В minikube:

```bash
minikube ssh
ps aux | grep kube-scheduler
# или
crictl ps | grep scheduler
```

В production-кластере:

```bash
kubectl get pods -n kube-system | grep scheduler
kubectl logs -n kube-system kube-scheduler-minikube
```

### Типичные причины, почему под висит в состоянии Pending

- Нет подходящей ноды (все отфильтрованы)
- Недостаточно ресурсов (CPU/memory)
- Taints/tolerations не совпадают
- NodeAffinity / nodeSelector не подходит
- Максимум подов на ноде достигнут

### Коротко одним предложением

**kube-scheduler** — это «диспетчер рейсов» Kubernetes: он постоянно ищет
свободные и подходящие ноды для новых подов, фильтрует неподходящие, ранжирует
лучшие и назначает поду ноду, чтобы kubelet мог его запустить.

Если интересно — могу подробнее рассказать про:

- как настраивать scoring и filtering
- что такое scheduler extender и scheduler plugins
- как работает leader election
- как посмотреть, почему под не размещается (kubectl describe pod)

# kube-controller-manager

**kube-controller-manager** — это один из ключевых компонентов **control plane**
Kubernetes, который отвечает за **поддержание желаемого состояния** кластера в
реальности.

Простыми словами: это «надзиратель», который постоянно смотрит:  
«А всё ли так, как должно быть? Если нет — исправляю».

### Что именно делает kube-controller-manager

kube-controller-manager — это **единый процесс**, внутри которого запущено *
*множество независимых контроллеров** (controllers). Каждый контроллер отвечает
за какой-то конкретный тип ресурса или аспект кластера.

Самые важные и известные контроллеры внутри него:

| Контроллер                    | За что отвечает простыми словами                                                                          |
|-------------------------------|-----------------------------------------------------------------------------------------------------------|
| **ReplicationController**     | Следит, чтобы всегда было ровно столько подов, сколько указано в replicas (старый, почти не используется) |
| **ReplicaSet**                | То же самое, но для Deployment (более современный)                                                        |
| **Deployment**                | Управляет rollout'ами, rollback'ами, обновлениями версий приложения                                       |
| **StatefulSet**               | Управляет stateful-приложениями (порядок подов, стабильные имена, PVC)                                    |
| **DaemonSet**                 | Гарантирует, что на каждой (или выбранных) нодах запущен один под (например, node-exporter, fluentd)      |
| **Job** / **CronJob**         | Следит за выполнением разовых задач и периодических заданий                                               |
| **Node**                      | Следит за состоянием нод (NotReady → удаляет поды, добавляет taints и т.д.)                               |
| **Endpoints / EndpointSlice** | Обновляет списки IP подов для Service (когда поды добавляются/удаляются)                                  |
| **ServiceAccount**            | Управляет токенами сервис-аккаунтов (устаревшая часть, сейчас больше через TokenRequest API)              |
| **Garbage Collector**         | Удаляет «осиротевшие» объекты (например, поды без владельца)                                              |
| **TTL Controller**            | Удаляет Jobs по истечении TTL (если включено)                                                             |
| **Namespace**                 | Управляет жизненным циклом namespace                                                                      |

### Как это работает (reconciliation loop)

Каждый контроллер работает по одному и тому же принципу — **цикл примирения** (
reconciliation loop):

1. **Смотрит желаемое состояние** (из etcd через kube-apiserver)  
   Например: в Deployment указано replicas: 5

2. **Смотрит текущее состояние** (тоже через apiserver)  
   Сейчас запущено только 3 пода

3. **Вычисляет расхождение**  
   Нужно создать ещё 2 пода

4. **Делает действия**  
   Создаёт новые ReplicaSet → поды → scheduler их размещает → kubelet запускает

5. Повторяет бесконечно (каждые несколько секунд)

Если контроллер упал — kube-controller-manager перезапускает его автоматически.

### Важные особенности

- **Один процесс — много контроллеров**  
  Все они живут в одном бинарнике kube-controller-manager.  
  Можно запускать несколько реплик (HA), но работает только **лидер** (leader
  election через lease в etcd).

- **Не запускает поды сам**  
  Только создаёт объекты (ReplicaSet, Job и т.д.).  
  Запуск — задача kubelet.

- **Stateless**  
  Не хранит состояние — всё читает из apiserver/etcd.

- **Можно отключать отдельные контроллеры**  
  Флаг `--controllers=*,-garbagecollector` — отключает сборщик мусора, например.

- **Логи и мониторинг**  
  Очень полезно смотреть логи kube-controller-manager, когда что-то не так с
  контроллерами (Deployment не обновляется, поды не пересоздаются и т.д.).

### Как посмотреть в кластере

В minikube:

```bash
minikube ssh
ps aux | grep kube-controller-manager
# или
crictl ps | grep controller-manager
```

В production:

```bash
kubectl get pods -n kube-system | grep controller-manager
kubectl logs -n kube-system kube-controller-manager-minikube
```

### Коротко одним предложением

**kube-controller-manager** — это «самовосстанавливающийся надзиратель»
Kubernetes: он состоит из множества контроллеров, которые бесконечно сравнивают
желаемое состояние (из etcd) с реальным и исправляют расхождения, чтобы кластер
всегда был в том виде, как ты его описал в манифестах.

# kubelet

**kubelet** — это **самый важный агент**, который работает **на каждой рабочей
ноде** (worker node) кластера Kubernetes.  
Без kubelet нода считается «мёртвой» для кластера — она не может запускать поды,
и scheduler перестаёт на неё размещать новые задачи.

Простыми словами: kubelet — это «местный менеджер» на каждой машине кластера. Он
получает приказы от control plane и выполняет всю реальную работу по запуску и
поддержанию контейнеров.

### Основные обязанности kubelet (что он делает каждый день)

| Задача                               | Простыми словами                                                                     | Почему это важно                                        |
|--------------------------------------|--------------------------------------------------------------------------------------|---------------------------------------------------------|
| Регистрирует ноду в кластере         | Сообщает apiserver: «Я здесь, у меня столько CPU/памяти/диска, ОС такая-то»          | Кластер знает, какие ноды живы и чем они располагают    |
| Получает PodSpec от apiserver        | Берёт список подов, которые должны работать именно на этой ноде                      | Это «желаемое состояние» для ноды                       |
| Запускает и останавливает контейнеры | Через container runtime (containerd, CRI-O, Docker) тянет образы, создаёт контейнеры | Без этого поды не стартуют                              |
| Следит за здоровьем контейнеров      | Проверяет liveness/readiness/startup пробы, перезапускает упавшие контейнеры         | Автоматическое самовосстановление                       |
| Управляет томами (volumes)           | Монтирует PersistentVolume, ConfigMap, Secret, emptyDir и т.д.                       | Данные и конфиги попадают в контейнер                   |
| Применяет resource requests/limits   | Ограничивает CPU/память, чтобы один под не «съел» всю ноду                           | Защита от noisy neighbor                                |
| Отправляет статус обратно            | Сообщает apiserver: под Running/Failed/Pending, нода Ready/NotReady, метрики         | kubectl get pods/nodes показывает актуальную информацию |
| Выполняет graceful shutdown          | При удалении пода ждёт grace period, отправляет SIGTERM → SIGKILL                    | Приложения успевают корректно завершиться               |
| Игнорирует не-Kubernetes контейнеры  | Не трогает всё, что запущено вручную (docker run и т.п.)                             | Не конфликтует с другими процессами на ноде             |

### Как kubelet общается с остальным кластером

- **Только через kube-apiserver** — никогда напрямую с etcd, scheduler или
  controller-manager.
- Получает список подов через **watch** на API.
- Отправляет статус, метрики, события через API.
- Порт по умолчанию: 10250 (HTTPS) и 10255 (read-only HTTP, устаревший).

### Ключевые особенности (2026 год)

- **kubelet — единственный компонент**, который напрямую взаимодействует с *
  *container runtime** (через CRI — Container Runtime Interface).
- Работает как **демон** (systemd или статический под в kube-system).
- **Не HA** — на каждой ноде ровно один kubelet. Если упал — нода становится
  NotReady.
- Очень чувствителен к ресурсам ноды: если нода «задыхается» (OOM, CPU
  starvation) — kubelet может не успевать отвечать apiserver → нода помечается
  NotReady.
- Поддерживает **In-Place Pod Resize** (с 1.27 experimental → 1.35 stable) —
  позволяет увеличивать ресурсы контейнера без перезапуска (очень полезно для
  stateful-приложений).

### Как посмотреть kubelet в кластере

В minikube:

```bash
minikube ssh
ps aux | grep kubelet
# или
journalctl -u kubelet -f   # если systemd
```

В production:

```bash
# На самой ноде
systemctl status kubelet
journalctl -u kubelet -f

# С контрольной плоскости
kubectl get nodes
kubectl describe node worker-1   # → смотри Kubelet version, conditions, taints
```

### Коротко одним предложением

**kubelet** — это «локальный исполнитель» на каждой рабочей ноде: он получает от
apiserver список подов, запускает их через container runtime, следит за
здоровьем, монтирует тома, ограничивает ресурсы и постоянно отчитывается о
состоянии — без kubelet нода бесполезна для Kubernetes.

# kube-proxy

**kube-proxy** — это компонент Kubernetes, который работает **на каждой рабочей
ноде** (worker node) и отвечает за **реализацию сетевых правил для Service** (
ClusterIP, NodePort, LoadBalancer).

Простыми словами:  
kube-proxy — это «сетевой диспетчер» на каждой машине кластера. Он делает так,
чтобы когда кто-то обращается к виртуальному IP сервиса (ClusterIP), трафик
попадал на один из реальных подов, которые этот сервис обслуживают.

Без kube-proxy **Service** в Kubernetes просто не работали бы — трафик бы не
доходил до подов.

### Основные задачи kube-proxy

| Задача                           | Простыми словами                                                                |
|----------------------------------|---------------------------------------------------------------------------------|
| Реализует **ClusterIP**          | Делает виртуальный IP сервиса «живым» — трафик на него перенаправляется на поды |
| Реализует **NodePort**           | Открывает порт на всех нодах кластера (30000–32767) и перенаправляет трафик     |
| Реализует **LoadBalancer**       | В облаке — настраивает внешний LB, в minikube — работает через tunnel           |
| Балансирует трафик между подами  | Выбирает, на какой под отправить запрос (round-robin, least connection и т.д.)  |
| Обновляет правила при изменениях | Когда под добавляется/удаляется — kube-proxy мгновенно обновляет правила        |
| Поддерживает session affinity    | Может «приклеивать» клиента к одному поду (по IP или cookie)                    |

### Как kube-proxy работает технически (режимы)

kube-proxy настраивает правила в ядре Linux, чтобы трафик перенаправлялся **без
участия самого процесса kube-proxy** в каждом запросе. Есть три основных режима:

| Режим        | Как работает                                                      | Скорость / overhead | Когда использовать в 2026 году                     |
|--------------|-------------------------------------------------------------------|---------------------|----------------------------------------------------|
| **iptables** | Создаёт тысячи правил в цепочках NAT (по одному на сервис + поды) | Средняя (O(n))      | По умолчанию в маленьких кластерах, legacy         |
| **IPVS**     | Создаёт виртуальный сервер в ядре (хеш-таблица, O(1))             | Очень высокая       | Рекомендуется для средних/больших кластеров        |
| **nftables** | Новый режим (замена iptables), более современный и эффективный    | Высокая             | Будущее (в новых версиях K8s дефолт/рекомендуется) |

**В 2026 году**:

- **iptables** всё ещё дефолт в старых кластерах и minikube, но уже считается
  устаревшим.
- **IPVS** — золотая середина для большинства production-кластеров.
- **nftables** — активно внедряется (в Kubernetes 1.29+ можно включить, в 1.35+
  может стать дефолтом).

### Как kube-proxy узнаёт, что делать

1. kube-proxy **смотрит** через kube-apiserver на объекты **Service** и *
   *Endpoints/EndpointSlice**.
2. Когда появляется новый Service или меняется список подов — kube-proxy
   обновляет правила в ядре (iptables/IPVS/nftables).
3. Дальше **ядро Linux** само обрабатывает миллионы пакетов в секунду без
   участия kube-proxy.

### Как посмотреть kube-proxy в кластере

В minikube:

```bash
minikube ssh
ps aux | grep kube-proxy
# или
crictl ps | grep proxy
journalctl -u kube-proxy   # если systemd
```

В production:

```bash
kubectl get pods -n kube-system | grep kube-proxy
kubectl logs -n kube-system kube-proxy-abc123
```

Посмотреть текущий режим:

```bash
kubectl logs -n kube-system -l k8s-app=kube-proxy | grep -i "Using.*Proxier"
# Пример вывода:
# Using ipvs Proxier
# Using iptables Proxier
```

### Коротко одним предложением

**kube-proxy** — это сетевой компонент на каждой ноде, который настраивает
правила ядра Linux (iptables / IPVS / nftables), чтобы трафик на виртуальные IP
сервисов (ClusterIP, NodePort) попадал на реальные поды, обеспечивая
балансировку и доступность Service.

# CRI и containerd

**CRI** и **containerd** — это два очень важных понятия в современной
архитектуре Kubernetes, особенно после 2020–2021 годов, когда Docker был
официально вытеснен из core Kubernetes.

### Что такое CRI (Container Runtime Interface)

CRI — это **стандартный интерфейс** (спецификация), который Kubernetes
использует для общения с любым контейнерным runtime (программой, которая
запускает контейнеры).

Простыми словами: CRI — это «универсальная розетка», в которую Kubernetes (а
точнее kubelet) вставляет штекер, чтобы управлять контейнерами. Благодаря CRI
Kubernetes **не привязан** к конкретному runtime — можно использовать
containerd, CRI-O, gVisor, Kata Containers и даже Docker (через dockershim, но
он устарел).

**Ключевые моменты про CRI:**

- CRI появился в Kubernetes 1.5 (2016 год) как способ убрать жёсткую зависимость
  от Docker.
- kubelet **не знает**, какой именно runtime стоит на ноде — он общается только
  через CRI (gRPC-протокол).
- CRI определяет методы вроде: PullImage, CreateContainer, StartContainer, Exec,
  Logs, Inspect и т.д.
- С версии Kubernetes **1.24** (апрель 2022) **dockershim** был полностью
  удалён — теперь CRI обязателен для любого runtime.

### Что такое containerd

**containerd** — это **самый популярный и дефолтный** контейнерный runtime в
Kubernetes с 2020–2021 годов.

Простыми словами: containerd — это «лёгкая, быстрая и надёжная» программа,
которая умеет:

- тянуть образы из реестров (docker pull)
- распаковывать их
- запускать контейнеры (через runc — низкоуровневый OCI-runtime)
- останавливать, удалять, следить за ними
- предоставлять метрики и логи

**Почему containerd стал дефолтом:**

- Docker слишком тяжёлый (включает в себя daemon, CLI, networking, build и
  многое другое).
- containerd — это именно та часть Docker, которая отвечает **только за запуск
  контейнеров** (выделили в отдельный проект в 2017 году).
- containerd полностью соответствует CRI → kubelet работает с ним напрямую.
- Лёгкий (меньше памяти и CPU), быстрее стартует, меньше уязвимостей.
- Поддерживается CNCF (Cloud Native Computing Foundation).

### Сравнение: Docker vs containerd vs CRI-O

| Характеристика           | Docker (через dockershim, до 1.24) | containerd (CRI)                                          | CRI-O (CRI)                                       |
|--------------------------|------------------------------------|-----------------------------------------------------------|---------------------------------------------------|
| Статус в Kubernetes 2026 | Удалён (dockershim нет с 1.24)     | Дефолтный runtime в большинстве дистрибутивов             | Тоже очень популярен, особенно в OpenShift        |
| Размер / overhead        | Тяжёлый (полный Docker daemon)     | Лёгкий (~50–100 МБ)                                       | Очень лёгкий, минималистичный                     |
| Скорость запуска         | Медленнее                          | Быстрее                                                   | Обычно самый быстрый                              |
| Поддержка OCI-стандартов | Да, но с legacy                    | Полная (OCI runtime spec)                                 | Полная, изначально под Kubernetes                 |
| Кто использует           | Старые кластеры до 1.23            | Kubernetes, containerd-based дистрибутивы, minikube, kind | Red Hat OpenShift, MicroK8s, некоторые enterprise |
| CRI-совместимость        | Через dockershim (удалён)          | Полная (cri plugin)                                       | Полная (создан специально для CRI)                |

### Как это выглядит в реальном кластере

На ноде:

- kubelet → CRI (gRPC) → containerd (или CRI-O)
- containerd → runc (низкоуровневый runtime) → запускает контейнер в
  namespace/cgroups

В minikube (по умолчанию containerd с 1.20+):

```bash
minikube ssh
crictl ps                  # список контейнеров (аналог docker ps)
crictl info | grep runtime # покажет runtime
systemctl status containerd
```

### Коротко одним предложением

**CRI** — это стандартный интерфейс, через который kubelet управляет любым
контейнерным runtime, а **containerd** — лёгкий, быстрый и современный runtime (
де-факто стандарт в Kubernetes), который заменил тяжёлый Docker и напрямую
подключается к kubelet через CRI.

Если интересно — могу рассказать подробнее про:

- как переключить runtime в minikube (на CRI-O или gVisor)
- разницу между containerd и CRI-O в цифрах
- что такое runc и почему он в основе всего

# Pod Network (CNI)

**Pod Network (CNI)** — это одна из самых важных частей Kubernetes, которая
отвечает за **сеть между подами**.

Kubernetes требует, чтобы все поды в кластере могли общаться друг с другом *
*напрямую по IP**, без NAT и без сложных прокси. Именно это и обеспечивает **CNI
** (Container Network Interface).

### Что такое CNI простыми словами

CNI — это **стандарт интерфейса** (спецификация), который позволяет Kubernetes
подключать к любой сетевой реализации (плагину).  
Когда kubelet создаёт новый под, он вызывает CNI-плагин и говорит:  
«Дай этому поду уникальный IP в кластере и подключи его к сети, чтобы он мог
общаться с другими подами».

CNI-плагин выполняет всю грязную работу:

- присваивает IP поду
- создаёт виртуальный интерфейс (veth-пару)
- подключает его к мосту / VXLAN / BGP / eBPF
- настраивает маршруты на ноде
- иногда шифрует трафик, применяет NetworkPolicy и т.д.

### Основные требования Kubernetes к Pod Network (CNI должен их выполнять)

1. Каждый под получает **уникальный IP** во всём кластере (не только внутри
   ноды).
2. Поды общаются **напрямую по IP** без NAT (pod-to-pod communication).
3. Ноды могут общаться со всеми подами (и наоборот) без NAT.
4. Поддержка NetworkPolicy (если плагин умеет).

### Самые популярные CNI-плагины в 2025–2026 годах

| Плагин          | Тип сети                | Скорость / overhead | NetworkPolicy     | Overlay / Underlay | Самые частые сценарии использования                                 | Сложность настройки |
|-----------------|-------------------------|---------------------|-------------------|--------------------|---------------------------------------------------------------------|---------------------|
| **Flannel**     | Overlay (VXLAN)         | Средняя             | Нет               | Overlay            | Самый простой, для обучения, небольшие кластеры                     | ★☆☆☆☆               |
| **Calico**      | BGP или IPIP/VXLAN      | Высокая             | Да (очень мощные) | Underlay / Overlay | Крупные кластеры, security, NetworkPolicy                           | ★★★☆☆               |
| **Cilium**      | eBPF (native)           | Очень высокая       | Да (L3–L7)        | Underlay (eBPF)    | Современные production-кластеры, observability, security            | ★★★★☆               |
| **Weave Net**   | Overlay (Fast datapath) | Средняя             | Да (базовые)      | Overlay            | Простые кластеры, хорошая совместимость                             | ★★☆☆☆               |
| **Multus**      | Multi-CNI               | Зависит от плагинов | Зависит           | Любая              | Когда нужен несколько сетей в одном поде (например, storage + data) | ★★★★★               |
| **Kube-router** | BGP / iptables          | Высокая             | Да                | Underlay           | Лёгкий, без overlay, для bare-metal                                 | ★★★☆☆               |

### Как это работает на уровне ноды (очень упрощённо)

1. kubelet хочет создать под → вызывает CNI-плагин (через /etc/cni/net.d/
   конфиг).
2. CNI-плагин:
    - выделяет IP из пула (podCIDR ноды)
    - создаёт пару veth (один конец в поде, второй на хосте)
    - подключает veth-хост к мосту (cni0 / caliXXX / cilium_host и т.д.)
    - настраивает маршрут на ноде
3. Если под на другой ноде → плагин использует VXLAN / Geneve / BGP / eBPF для
   передачи пакета между нодами.

### Самые частые проблемы с CNI

- Поды в состоянии ContainerCreating долго висят → CNI не смог выделить IP или
  настроить сеть.
- Нет связи между подами на разных нодах → проблема с overlay/underlay, MTU,
  firewall.
- NetworkPolicy не работает → плагин не поддерживает или неправильно настроен.
- Высокий latency → overlay (VXLAN) добавляет overhead, лучше использовать
  underlay (Calico BGP, Cilium eBPF).

### Коротко одним предложением

**Pod Network (CNI)** — это система, которая даёт каждому поду уникальный IP в
кластере и обеспечивает прямую связь между всеми подами без NAT, а конкретную
реализацию выбираешь ты через CNI-плагин (Flannel, Calico, Cilium и т.д.), и
именно он отвечает за то, чтобы поды «видели» друг друга.
