# Масштабирование

**Горизонтальное и вертикальное масштабирование** — это два основных способа
увеличивать мощность системы (приложения, сервиса, кластера) при росте нагрузки.

В Kubernetes эти концепции реализуются очень чётко и по-разному, и они часто
используются вместе.

### Простая аналогия из жизни

Представь ресторан:

- **Горизонтальное масштабирование** (scale out / scale in)  
  → Когда посетителей становится много — нанимаешь дополнительных официантов (
  добавляешь больше копий одного и того же приложения).  
  Каждый официант обслуживает своих гостей → нагрузка распределяется.

- **Вертикальное масштабирование** (scale up / scale down)  
  → Даёшь существующему официанту **больше сил**: больший поднос, быстрее
  бегает, может обслужить больше столов одновременно (увеличиваешь CPU/память
  одному экземпляру).

### Как это выглядит в Kubernetes (2026 год)

| Параметр                   | Горизонтальное масштабирование (Horizontal)                                         | Вертикальное масштабирование (Vertical)                                                                      |
|----------------------------|-------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| Что именно масштабируется  | Количество копий (реплик) подов                                                     | Ресурсы (CPU и память) одного пода                                                                           |
| Основной механизм в K8s    | Horizontal Pod Autoscaler (**HPA**)                                                 | Vertical Pod Autoscaler (**VPA**)                                                                            |
| Когда лучше всего подходит | Приложения, которые легко распараллеливаются (stateless, web-сервисы, микросервисы) | Приложения, которые плохо параллелизуются или имеют пиковое потребление памяти/CPU                           |
| Автоматически?             | Да (по CPU, памяти, custom-метрикам)                                                | Да (рекомендации или авто-ресайз), но с оговорками                                                           |
| Перезапуск пода?           | Обычно нет (новые поды добавляются плавно)                                          | Да (в старых версиях VPA), но с K8s 1.35+ есть **In-Place Pod Resize** (без перезапуска в некоторых случаях) |
| Плюсы                      | Высокая доступность, отказоустойчивость, легко масштабировать почти бесконечно      | Экономия ресурсов, нет overhead от лишних подов                                                              |
| Минусы                     | Больше overhead (сеть, координация), нужен stateless-дизайн                         | Ограничено максимумом одной ноды, может вызвать downtime при ресайзе                                         |
| Пример команды / ресурса   | `kubectl autoscale deployment my-app --cpu-percent=70 --min=2 --max=10`             | Установка VPA + CRD VerticalPodAutoscaler                                                                    |
| Статус в K8s (2026)        | Полностью stable, v2 API                                                            | Stable (с 1.25+), In-Place Resize stable с 1.35 (по умолчанию включено)                                      |

### Ключевые механизмы в Kubernetes

- **HPA (Horizontal Pod Autoscaler)** — самый популярный и надёжный.  
  Автоматически увеличивает/уменьшает количество реплик Deployment/StatefulSet
  по метрикам (CPU 70%, память, запросы в секунду через custom metrics, KEDA для
  событий и т.д.).  
  Пример: нагрузка выросла → HPA создал 3 → 8 реплик → нагрузка упала → вернул к
    3.

- **VPA (Vertical Pod Autoscaler)** — add-on (не встроен по умолчанию).  
  Смотрит на реальное потребление пода и рекомендует/автоматически меняет
  requests/limits CPU и памяти.  
  Режимы:
    - `Off` — только рекомендации (самый безопасный для начала)
    - `Auto` — меняет и перезапускает под (может быть downtime)
    - С 1.35+ **In-Place Pod Vertical Scaling** — позволяет увеличивать ресурсы
      без перезапуска (очень круто для stateful-приложений).

- **Комбинация HPA + VPA** — золотой стандарт в production 2025–2026.  
  Сначала VPA помогает правильно подобрать requests/limits (чтобы не
  переплачивать), потом HPA масштабирует количество реплик по нагрузке.

### Когда что выбирать

- **Горизонтальное** (HPA):
    - Веб-приложения, API, микросервисы
    - Нагрузка сильно колеблется
    - Нужно быстро реагировать на пики
    - Приложение stateless или state вынесен наружу (Redis, DB)

- **Вертикальное** (VPA):
    - Приложения с переменным, но не очень параллельным потреблением (
      batch-задачи, ML-инференс)
    - Хочешь сэкономить ресурсы (overprovisioning 30–70%)
    - Нельзя просто добавить реплик (например, монолит или stateful без
      шардинга)

- **Вместе**:  
  VPA → оптимизирует размер каждого пода  
  HPA → добавляет/убирает эти оптимизированные поды по нагрузке  
  Cluster Autoscaler / Karpenter → добавляет/убирает ноды под выросшее
  количество подов

Если коротко:  
**Горизонтальное** — "больше одинаковых официантов", быстро, отказоустойчиво,
стандарт в облаке.  
**Вертикальное** — "даём официанту суперсилы", экономно, но сложнее и с рисками
перезапуска.

# Ручное масштабирование

Для ручного масштабирования указывается количество реплик:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: timeserver
spec:
  replicas: 7 # /-> Указывается количество реплик
  selector:
    matchLabels:
      pod: timeserver-pod
  template:
    metadata:
      labels:
        pod: timeserver-pod
    spec:
      containers:
        - name: timeserver-container
          image: docker.io/wdenniss/timeserver:3
          resources:
            requests:
              cpu: 200m
              memory: 250Mi
```

# Автоматическое масштабирование подов

## HPA

В состав Kubernetes входит так называемый горизонтальный автоскейлер подов
(Horizontal Pod Autoscaler, HPA), который позволяет указать для пода целевое
значение такого показателя, как потребление ресурсов процессора, и некоторые
пределы масштабирования (минимальное и максимальное количество реплик).
После этого HPA начинает следить за тем, чтобы выбранный вами показатель
стремился к указанному значению, создавая или удаляя реплики пода. Так, если
вы укажете, что потребление ресурсов процессора должно составлять 20 %, то
HPA будет увеличивать количество реплик в том случае, когда среднее потребле-
ние ресурсов процессора (в рамках всех подов) будет подниматься выше 20 % (от
количества ресурсов, запрашиваемого подами в своих ресурсных требованиях),
и уменьшать количество реплик, когда этот показатель будет опускаться ниже 20 %.
Эти действия будут выполняться в рамках заданных вами пределов и с определен-
ной задержкой во избежание излишней поспешности.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: timeserver
spec:
  minReplicas: 1 # Минимальное количество реплик
  maxReplicas: 10 # Максимальное количество реплик 
  metrics:
    - resource:
        name: cpu
        target:
          averageUtilization: 20 # Целевое значение показателя потребления ресурсов
          # процессора. HPA будет создавать дополнительные реплики
          # в том случае, если данный показатель будет подниматься выше
          # указанного значения
          type: Utilization
      type: Resource
  scaleTargetRef: # Развертывание, которое
    # будет подвергаться
    # масштабированию
    apiVersion: apps/v1
    kind: Deployment
    name: timeserver
```

## VPA

Под вертикальным автомасштабированием подов (Vertical Pod Autoscaling, VPA)
понимается процесс, при котором поды масштабируются вертикально путем
изменения количества предоставляемых им ресурсов процессора и памяти.
В Kubernetes это реализуется путем отслеживания потребности подов в ресур-
сах и динамического изменения их запросов ресурсов с течением времени.
В Kubernetes нет встроенной реализации вертикального автоскейлера, но вы
можете использовать реализацию, созданную в рамках проекта с открытым
исходным кодом (https://github.com/kubernetes/autoscaler). Кроме того, собствен-
ную реализацию вертикального автоскейлера предлагают и многие облачные
платформы, в том числе сервис GKE.
Вертикальный автоскейлер подов автоматически отслеживает потребности
подов в ресурсах, поэтому благодаря его применению вы сможете тратить
меньше усилий и более эффективно использовать ресурсы. Кроме того, он бу-
дет полезен и в том случае, когда нужно обеспечить динамическое изменение
запросов ресурсов подов с течением времени (при значительном колебании
запросов подов).
Использование вертикального автоскейлера несколько увеличивает уровень
сложности системы, к тому же он не всегда хорошо взаимодействует с гори-
зонтальным автоскейлером. Поэтому я рекомендую не торопиться с его при-
менением, начав с определения для подов корректных запросов ресурсов
и использования горизонтального автоскейлера.


## Масштабирование узлов

Использование горизонтального автомасштабирования подов — прекрасный спо-
соб обеспечить автоматическое масштабирование подов по мере необходимости.
Но если при этом вы будете вручную масштабировать узлы в целях наращивания
и сокращения мощностей, то управление процессом будет по-прежнему требовать
постоянного участия человека. Используя распространенный инструмент автомас-
штабирования кластера (Cluster Autoscaler), вы также сможете обеспечить автома-
тическое масштабирование узлов по мере необходимости, что хорошо сочетается
с использованием горизонтального автоскейлера для масштабирования подов.



### Автомасштабирование кластера

Автомасштабирование кластера не относится к числу функций, предоставляемых
базовым API Kubernetes, являясь необязательным компонентом. К счастью, боль-
шинство облачных провайдеров предоставляет эту функциональность (или нечто
подобное) в виде встроенного свойства платформы, позволяющего обеспечить
автоматическое масштабирование количества узлов, чтобы вы могли сосредото-
читься только на своем приложении и необходимом для него количестве реплик.
Данная функциональная возможность зависит от платформы, поэтому у каждого
провайдера она реализована по-своему (а у некоторых провайдеров ее вообще нет).
Чтобы найти нужную вам документацию, попробуйте ввести в браузере поисковый
запрос «[Ваш облачный сервис] Cluster Autoscaler».


### Свободные мощности при автомасштабировании кластера

Одним из недостатков автомасштабирования узлов по сравнению с добавлением
узлов вручную является то, что иногда автоскейлер выполняет масштабирование
слишком точно, не оставляя никаких свободных мощностей. Это большой плюс
с точки зрения экономии затрат, в то же время такое поведение автоскейлера ведет
к более медленному запуску новых подов, поскольку для них требуется выделять
дополнительные мощности.
Запуск новых подов с предварительным добавлением новых узлов занимает больше
времени, чем их запуск на уже существующих узлах. При этом приходится сначала
выделять и запускать новые узлы, в то время как при распределении подов на уже
существующие узлы достаточно просто извлечь контейнер и запустить под. Если
контейнер уже находится в кэше, то к запуску пода можно будет приступить сразу
же. 

Один из способов решения этой проблемы без отказа от автомасштабирования узлов
сводится к использованию низкоприоритетных временных подов-заполнителей,
единственная задача которых — резервирование мощностей (путем поддержания
в состоянии готовности дополнительных узлов). Этим временным подам-заполни-
телям присваивается низкий приоритет, чтобы при масштабировании ваши рабо-
чие нагрузки могли вытеснить их, подвергнув приоритизации, и воспользоваться
освободившимися мощностями. 

Чтобы создать временное развертывание для своего пода, сначала нужно опреде-
лить класс приоритета (объект PriorityClass). Значение этого класса должно быть
меньше нуля (поскольку нам нужно, чтобы при выполнении приоритизации его
мог вытеснить любой другой класс приоритета)

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: placeholder-priority
value: -10
preemptionPolicy: Never
globalDefault: false
description: "Placeholder Pod priority."


---
# Deploy:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: placeholder
spec:
  replicas: 10
  selector:
    matchLabels:
      pod: placeholder-pod
  template:
    metadata:
      labels:
        pod: placeholder-pod
    spec:
      priorityClassName: placeholder-priority
      terminationGracePeriodSeconds: 0
      containers:
        - name: ubuntu
          image: ubuntu
          command: ["sleep"]
          args: ["infinity"]
          resources:
            requests:
              cpu: 200m
              memory: 250Mi

```
