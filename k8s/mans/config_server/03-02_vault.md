# Vault

>а можешь еще рассказать по vault? это какой-то микросервис, что-то типа Spring Cloud Config, только в нем хранится не просто конфигурация, а ключи и токены?

Вы правы, HashiCorp Vault — это не просто аналог Spring Cloud Config, а инструмент, решающий более глубокий класс задач. Если Config Server — это централизованное хранилище **всей** конфигурации, то Vault — это специализированное, максимально защищенное хранилище для **секретов**.

### 🔐 Что такое Vault и чем он отличается от Config Server

HashiCorp Vault — это система управления секретами и шифрования на основе идентификации. Секретом может быть всё, что требует строгого контроля доступа: пароли, API-ключи, сертификаты, токены.

Ключевое отличие от Config Server заключается в подходе к безопасности и возможностях:

*   **Назначение**: Config Server централизует **всю** конфигурацию (включая нечувствительные данные). Vault же предназначен исключительно для хранения **секретов**.
*   **Динамические секреты**: Это киллер-фича Vault. Он может **генерировать** учетные данные для базы данных, облачного провайдера и т.д. "на лету" и с ограниченным сроком жизни (TTL), после чего автоматически их отзывает. Config Server так не умеет — он хранит статические значения.
*   **Аудит и контроль доступа**: Vault предоставляет детальный аудит всех операций с секретами и использует мощную систему политик (на основе путей) для разграничения доступа.
*   **Хранение**: Секреты в Vault **всегда зашифрованы** (шифруются при сохранении и расшифровываются только в памяти). В Git, который часто используется для Config Server, секреты лежат в открытом виде, если не применять дополнительное шифрование.

### 🔄 Как Vault интегрируется в вашу архитектуру

В мире Spring Boot для работы с Vault используется проект **Spring Cloud Vault**. Он позволяет вашему приложению подключаться напрямую к Vault, без промежуточного сервера, как в случае с Config Server.

Процесс выглядит так:
1.  **Аутентификация**: Ваше приложение (`tasks-service`) при старте аутентифицируется в Vault. Для Kubernetes это делается автоматически с помощью **сервисного аккаунта** (Service Account). Vault проверяет токен этого аккаунта, который смонтирован в под по пути `/var/run/secrets/kubernetes.io/serviceaccount/token`.
2.  **Авторизация**: После аутентификации Vault выдает приложению временный токен. С этим токеном приложение может запрашивать секреты, но только те, на которые у него есть права согласно политикам.
3.  **Получение секретов**: Spring Cloud Vault монтирует секреты из Vault как источники свойств (property sources), и вы можете использовать их в своем коде точно так же, как и любые другие настройки.

### ⚙️ Пример настройки для вашего `tasks-service`

Чтобы `tasks-service` мог получать секреты из Vault, нужно добавить зависимость и настроить её.

1.  **Добавьте зависимость** в `pom.xml`:
    ```xml
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-vault-config</artifactId>
    </dependency>
    ```

2.  **Настройте `application.yaml`**:
    ```yaml
    spring:
      config:
        import: "optional:vault://" # Импортируем конфигурацию из Vault
      cloud:
        vault:
          host: vault.default.svc.cluster.local # Адрес сервиса Vault в кластере
          port: 8200
          scheme: http
          authentication: KUBERNETES # Используем аутентификацию через Kubernetes
          kubernetes:
            role: tasks-service-role # Имя роли, настроенной в Vault
    ```
    **Важно**: Строка `spring.config.import: "optional:vault://"` говорит Spring Boot использовать Vault как источник конфигурации.

### 💡 Ключевой момент: Динамические секреты и `@RefreshScope`

Самое интересное начинается, когда Vault генерирует **динамические** учетные данные для вашей MongoDB. У этих credentials есть срок жизни (TTL), и когда он истекает, Vault их отзывает.

Ваше приложение должно быть готово к смене пароля. Здесь на помощь снова приходит `@RefreshScope`:
1.  Когда Vault обновляет credentials, вам нужно инициировать обновление конфигурации в приложении (например, через вызов `/actuator/refresh`).
2.  Бины, помеченные `@RefreshScope`, будут пересозданы с новыми значениями из Vault.
3.  Это позволяет приложению использовать постоянно меняющиеся учетные данные без перезапуска.

### 💎 Итог

Vault — это не замена, а **дополнение** к Config Server. В production-среде их часто используют вместе:
*   **Spring Cloud Config Server**: для хранения всей несекретной конфигурации (настройки логирования, таймауты, флаги фич).
*   **HashiCorp Vault**: для управления секретами (пароли, API-ключи) и, что важнее, для генерации динамических учетных данных с ограниченным сроком жизни.

Для вашего учебного проекта использование Vault — это следующий уровень понимания безопасности в микросервисах, который демонстрирует умение работать с чувствительными данными профессионально.

> а почему используется spring.config.import: "optional:vault://"  ? ведь по этому адрему указан configserver.

Отличный вопрос. Это как раз тот момент, где Spring Boot проявляет свою гибкость. Дело в том, что `spring.config.import` — это не привязка к одному конкретному серверу, а **список источников**, которые Spring Boot может обрабатывать **последовательно**.

### 🎯 `configserver:` и `vault://` — это два разных мира

Важно разделять эти понятия:

*   **`configserver:`**: Это префикс для **Spring Cloud Config Server**. Он используется для получения **обычной конфигурации** (настройки логирования, таймауты, URL-адреса и т.д.) из Git-репозитория.
*   **`vault://`**: Это префикс для **HashiCorp Vault**. Он используется для получения **секретов** (пароли, API-ключи, токены).

Это два разных, независимых сервиса, которые решают разные задачи.

### 🔗 Как их можно использовать вместе

Spring Boot позволяет указать в `spring.config.import` **несколько источников через запятую**. Именно так их и объединяют в реальных проектах:

```yaml
spring:
  config:
    import: "optional:configserver:http://config-server:8888, optional:vault://"
```

Это говорит Spring Boot: «Сначала попробуй загрузить конфигурацию из Config Server, а затем — секреты из Vault». Порядок здесь важен, так как он определяет приоритет свойств.

### 🤔 Почему в вашем примере был только `vault://`

В том примере, который я приводил ранее, фокус был именно на **демонстрации работы с Vault**. Чтобы не усложнять, я показал минимально необходимую настройку для его подключения, опустив `configserver:`. В реальном проекте вы, скорее всего, захотите использовать **оба** источника.

### 💡 Что означает `optional:`

Префикс `optional:` (необязательный) означает, что если указанный сервис (Config Server или Vault) **недоступен**, приложение **всё равно запустится**, просто без этих настроек. Без этого префикса приложение упадёт с ошибкой, если не сможет подключиться к источнику.

### 💎 Итог

*   **`configserver:`** и **`vault://`** — это два разных источника конфигурации, которые можно и нужно использовать вместе.
*   В `spring.config.import` их можно перечислить через запятую, чтобы Spring Boot загрузил их последовательно.
*   **`optional:`** делает импорт необязательным, повышая отказоустойчивость приложения при старте.

Поэтому в вашем финальном проекте правильнее будет указать оба источника, чтобы разделить управление обычной конфигурацией и секретами.


> я стал перечитывать про vault и у меня появился вопрос: что же такое vault? это что-то типа сервера хранения учетных данных?

Да, вы ухватили суть, но Vault — это **больше**, чем просто «сервер хранения учётных данных». Он решает три задачи, которые Kubernetes Secret и Spring Cloud Config решить не могут.

## 🎯 Vault — это три инструмента в одном

### 1. Хранилище секретов (как Secret, но безопаснее)

Вы кладёте туда пароли, токены, ключи — и приложение запрашивает их при старте. Это **базовая** функция, похожая на Kubernetes Secret или Config Server. Но с важными отличиями:

| | Kubernetes Secret | Vault |
|---|---|---|
| Хранение | Base64 в etcd | **Зашифровано** (AES-256) |
| Доступ | RBAC K8s | **Своя система политик** + аудит |
| Аудит | Нет | **Каждый запрос логируется** |
| UI | Нет | **Веб-интерфейс** |
| Ротация | Вручную | **Автоматически** |

### 2. Динамические секреты — «киллер-фича»

Это то, чего **нет** ни у Kubernetes Secret, ни у Config Server.

**Проблема статических паролей:** у вас в Secret лежит `mongodb://rootadmin:password@...`. Этот пароль:
- Живёт вечно.
- Один на всех (все поды используют его).
- Если утёк — нужно менять вручную и перезапускать всё.

**Решение Vault:** приложение запрашивает у Vault доступ к MongoDB, и Vault **создаёт уникального пользователя** специально для этого приложения:

```
tasks-service → Vault: «дай доступ к MongoDB»
Vault → MongoDB: «создай пользователя tasks-svc-x7k2 с паролем abc123 на 1 час»
Vault → tasks-service: «вот логин tasks-svc-x7k2, пароль abc123, TTL 1 час»
```

Через час Vault **автоматически удалит** этого пользователя из MongoDB. Приложение запросит нового. Пароли никогда не повторяются, утечка одного ничего не даёт.

### 3. Шифрование как сервис (Encryption as a Service)

Vault умеет шифровать и расшифровывать данные **по запросу**, не храня ключи у вас:

```
Приложение → Vault: «зашифруй вот эти данные»
Vault → Приложение: «вот зашифрованный текст»
```

Ключи шифрования живут **только в Vault**. Приложение их никогда не видит. Это удобно для шифрования данных в БД, токенов, PII.

## 🏗️ Как Vault выглядит физически

Vault — это **отдельное приложение** (как Config Server), которое:

1. Разворачивается в Kubernetes (Deployment + Service) или на отдельной машине.
2. Хранит зашифрованные данные в **своём** backend'е:
   - Файловая система
   - Consul
   - etcd
   - Облачные хранилища (AWS S3, GCP)
3. Предоставляет **HTTP API** (и CLI, и UI) для доступа.
4. Имеет **свою систему аутентификации**: токены, Kubernetes ServiceAccount, LDAP, OIDC, AWS IAM.

```
┌──────────────────┐
│ Приложение       │
│ (tasks-service)  │
└────────┬─────────┘
         │ 1. Аутентификация (K8s ServiceAccount)
         │ 2. Запрос секрета
         ▼
┌──────────────────┐
│ Vault Server     │
│ - Auth methods   │
│ - Policies       │
│ - Secret engines │
│ - Audit log      │
└────────┬─────────┘
         │ Шифрованные данные
         ▼
┌──────────────────┐
│ Backend (etcd,   │
│ Consul, file...) │
└──────────────────┘
```

## 🔑 Ключевые концепции Vault

| Концепция | Что это |
|---|---|
| **Secret Engine** | «Движок» для работы с секретами. Бывают: KV (ключ-значение), Database (динамические credentials), AWS, PKI (сертификаты), Transit (шифрование) |
| **Auth Method** | Способ аутентификации: Kubernetes, Token, LDAP, OIDC, AWS IAM |
| **Policy** | Правила доступа: «этот сервис может читать секреты по пути `secret/data/tasks-service/*`» |
| **Path** | Адрес секрета: `secret/data/tasks-service/mongodb` |
| **Lease / TTL** | Срок жизни секрета. По истечении — автоматически отзывается |
| **Seal / Unseal** | Vault при старте «запечатан». Чтобы расшифровать данные, нужно «распечатать» его ключами (Shamir's Secret Sharing) |
| **Audit Device** | Логирование всех операций: кто, что, когда запросил |

## 🆚 Vault vs Kubernetes Secret vs Config Server

| Аспект | K8s Secret | Spring Cloud Config | Vault |
|---|---|---|---|
| Что хранит | Секреты | Всю конфигурацию | Секреты + динамические credentials |
| Где хранит | etcd (base64) | Git (plaintext) | Свой backend (зашифровано) |
| Шифрование | Опционально (Encryption at Rest) | Нет | **Всегда** |
| Аудит | Нет | Git history | **Детальный** |
| Динамические секреты | Нет | Нет | **Да** |
| Ротация | Вручную | Вручную | **Автоматически** |
| Отзыв доступа | Удалить Secret + перезапуск | Изменить Git + перезапуск | **Мгновенно, по TTL** |
| Сложность | Низкая | Средняя | **Высокая** |
| Когда использовать | Простые секреты в K8s | Централизованная конфигурация | Высокие требования к безопасности |

## 💡 Пример: как это работает в вашем случае

**Сейчас (K8s Secret):**
```yaml
env:
  - name: MONGO_URI
    valueFrom:
      secretKeyRef:
        name: mongodb-credentials
        key: MONGO_URI
```
Один статический пароль `rootadmin:supersecretpassword` для всех подов, живёт вечно.

**С Vault:**
```yaml
spring:
  config:
    import: "vault://"
  cloud:
    vault:
      authentication: KUBERNETES
      kubernetes:
        role: tasks-service
      mongodb:
        enabled: true
        role: tasks-service-role
```
При старте `tasks-service`:
1. Аутентифицируется в Vault через свой ServiceAccount.
2. Vault создаёт **уникального** пользователя в MongoDB с TTL 1 час.
3. Приложение получает логин/пароль, живёт с ними час.
4. Vault автоматически удаляет пользователя по истечении TTL.
5. Приложение запрашивает нового.

**Разница:** вместо одного вечного пароля — уникальные временные credentials для каждого пода.

## 🎯 Что запомнить

| Вопрос | Ответ |
|---|---|
| Vault — это сервер? | Да, отдельное приложение (как Config Server) |
| Что хранит? | Секреты, зашифрованные |
| Чем отличается от K8s Secret? | Шифрование, аудит, политики, динамические секреты |
| Чем отличается от Config Server? | Config Server — для всей конфигурации, Vault — только для секретов |
| Главная фича? | **Динамические секреты** — уникальные credentials с TTL |
| Сложно ли? | Да, это самый сложный инструмент из трёх |
| Нужен ли в учебном проекте? | Не обязательно, но понимание — плюс на собеседовании |

**Vault — это «сейф» для секретов с фантастическими возможностями:** он не просто хранит пароли, а **создаёт их на лету**, **отзывает по расписанию**, **логирует каждый доступ** и **шифрует всё, что внутри**. Kubernetes Secret — это «ящик стола с замком», Vault — «банковское хранилище с биометрией и охраной».

> а как получить, например логин/пароль? я имею ввиду, на примере настройки доступа к mongodb - в tasks-service deployment есть параметр с сылкой на БД и где то тут же должна быть какая-то запись "логин/пароль брать из vault". что то типа такого?

Да, вы уловили суть: в конфигурации приложения появляется блок, который говорит Spring, что нужно обратиться к Vault, а не искать логин/пароль в переменных окружения. Но, в отличие от Kubernetes Secret, здесь нет прямой ссылки на конкретное значение. Вместо этого Spring Cloud Vault **автоматически** помещает полученные от Vault динамические учетные данные в стандартные свойства MongoDB.

### 🔑 Как это работает: Автоматическая подстановка

Spring Cloud Vault устроен очень изящно. Когда он получает от Vault логин и пароль для MongoDB, он не требует, чтобы вы вручную прописывали их в URI. Вместо этого он сохраняет их в свойства `spring.data.mongodb.username` и `spring.data.mongodb.password`.

А поскольку вы используете Spring Boot, он **автоматически** подхватывает эти свойства и использует их для аутентификации в MongoDB. Вам не нужно писать какой-либо код для этого.

### 📝 Пример конфигурации для `tasks-service`

Вот как это будет выглядеть в вашем `application.yaml` (или в файле, который отдаёт Config Server):

```yaml
spring:
  config:
    import: "vault://" # Включаем Vault как источник конфигурации
  
  cloud:
    vault:
      authentication: KUBERNETES # Аутентификация через Service Account
      kubernetes:
        role: tasks-service-role # Роль, настроенная в Vault для вашего сервиса
      
      mongodb:
        enabled: true
        role: tasks-service-role # Роль MongoDB, настроенная в Vault
        # Spring Cloud Vault автоматически положит креды в эти свойства:
        # username-property: spring.data.mongodb.username (по умолчанию)
        # password-property: spring.data.mongodb.password (по умолчанию)
```

**Разбор ключевых моментов:**

*   **`spring.config.import: "vault://"`**: Эта строка активирует интеграцию с Vault.
*   **`authentication: KUBERNETES`**: Spring Cloud Vault будет использовать токен Kubernetes Service Account, который автоматически смонтирован в под по пути `/var/run/secrets/kubernetes.io/serviceaccount/token`, для аутентификации в Vault.
*   **`kubernetes.role`**: Имя роли, которую вы создали в Vault. Vault использует её, чтобы понять, какому сервисному аккаунту и из какого namespace можно аутентифицироваться, и какие политики к нему применить.
*   **`mongodb.enabled: true`** и **`mongodb.role`**: Эти параметры включают интеграцию с секретным движком баз данных и указывают, какую роль использовать для генерации учетных данных в MongoDB.

### 🚀 Что происходит при старте `tasks-service`

1.  **Аутентификация**: Приложение стартует и отправляет в Vault свой Kubernetes Service Account токен, указывая роль `tasks-service-role`.
2.  **Генерация**: Vault проверяет, что это за под, и, если всё верно, дает команду MongoDB создать нового пользователя с ограниченным сроком жизни (TTL) для этого конкретного экземпляра `tasks-service`.
3.  **Получение**: MongoDB создаёт пользователя и возвращает логин/пароль Vault'у. Vault, в свою очередь, отдаёт их вашему приложению.
4.  **Автоматическая настройка**: Spring Cloud Vault кладёт эти логин и пароль в свойства `spring.data.mongodb.username` и `spring.data.mongodb.password`.
5.  **Подключение**: Spring Boot "видит" эти свойства и использует их для создания подключения к MongoDB, даже не подозревая, что они пришли откуда-то извне.

### 💡 Важное замечание по вашему текущему URI

В вашем `config-repo/tasks-service.yaml` сейчас, скорее всего, указан полный URI с логином и паролем. При использовании Vault эту часть нужно будет убрать, оставив только адрес базы:

**Было (со статическим паролем):**
```yaml
spring:
  mongodb:
    uri: mongodb://rootadmin:supersecretpassword@tasks-mongodb-service:27017/tasksdb?authSource=admin
```

**Станет (с Vault):**
```yaml
spring:
  mongodb:
    uri: mongodb://tasks-mongodb-service:27017/tasksdb
    # Spring Cloud Vault автоматически добавит username и password
```

Spring Boot при наличии свойств `username` и `password` соберёт финальную строку подключения сам.

Да, вы абсолютно правы: HashiCorp Vault — это отдельный сервер, который чаще всего упаковывается в Docker-образ и запускается как самостоятельное приложение (или как Pod в вашем Kubernetes-кластере).
В контексте вашего микросервиса tasks-service Vault заменяет собой привычный файл application.properties (или yaml) в части хранения секретных данных (пароли от БД, API-ключи, токены). Вместо того чтобы хранить пароли в Git или передавать их через переменные окружения, ваш сервис при старте сам идёт в Vault и забирает их оттуда.

Что делает зависимость spring-cloud-vault?

Когда вы добавляете spring-cloud-vault-config в ваш tasks-service, происходит следующее:
1. Интеграция в Bootstrap-фазу: При запуске Spring Boot (еще до создания бинов вашей БД) библиотека перехватывает управление.
2. Аутентификация: Она обращается к серверу Vault и доказывает, что tasks-service — это именно тот сервис, за который он себя выдает (в Kubernetes это делается автоматически через ServiceAccount).
3. Загрузка секретов: Библиотека скачивает нужные секреты по указанному пути (например, secret/tasks-service).
4. Маппинг в PropertySource: Полученные секреты плавно внедряются в среду Spring. Вы можете использовать их точно так же, как обычные проперти — через @Value("${my.secret}") или в настройках подключения к БД (spring.datasource.password).
Куда она добавляется? В файл сборщика проекта (pom.xml для Maven или build.gradle для Gradle).

Что нужно сделать, чтобы подключить tasks-service к Vault?

Процесс состоит из 4 основных шагов:

1. Развернуть сервер Vault

В K8s проще всего установить Vault через официальный Helm-чарт. В режиме разработки его можно запустить одной командой внутри кластера или локально в Docker:
bash
docker run -d --name vault -p 8200:8200 -e 'VAULT_DEV_ROOT_TOKEN_ID=my-root-token' hashicorp/vault
Используйте код с осторожностью.

2. Добавить зависимость в tasks-service

Добавьте стартер в ваш pom.xml (не забудьте подключить Spring Cloud BOM для управления версиями):
xml
<dependency>
    <groupId>https://github.com</groupId> <!-- Концептуально -->
    <artifactId>spring-cloud-starter-vault-config</artifactId>
</dependency>
Используйте код с осторожностью.

3. Настроить конфигурацию подключения

В современных версиях Spring Boot (3.x+) подключение настраивается в файле application.yml:
yaml
spring:
  application:
    name: tasks-service
  config:
    import: "vault://" # Указывает Spring искать настройки в Vault
  cloud:
    vault:
      uri: http://vault-server-url:8200 # Адрес вашего Vault
      # Для локальной разработки обычно используют токен:
      token: my-root-token 
      # Для Kubernetes здесь настраивается кубер-аутентификация (см. ниже)
Используйте код с осторожностью.

4. Перенести секреты в Vault

Вы заходите в UI Vault (или через CLI) и создаете секрет по пути, который Spring Boot ожидает по умолчанию: secret/tasks-service. Например:
• Ключ: spring.datasource.password
• Значение: super-secret-db-pass
При старте tasks-service сам заберет этот пароль и подставит в конфигурацию базы данных.

Как это работает в Kubernetes (Best Practice)

В проде вводить token вручную в конфигурацию нельзя. В Kubernetes используется Kubernetes Authentication Method:
1. Ваш tasks-service запускается под определенным ServiceAccount.
2. spring-cloud-vault берет JWT-токен этого ServiceAccount (он лежит в каждом поде по умолчанию).
3. Библиотека отправляет этот токен в Vault.
4. Vault проверяет токен в API Kubernetes: "Действительно ли этот под существует и имеет эту роль?".
5. Если все ок, Vault выдает вашему сервису временный токен для чтения секретов tasks-service.
