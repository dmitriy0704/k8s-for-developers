В Kubernetes ограничение скорости (rate limiting) с использованием Redis работает как глобальный распределенный счетчик, так и в виде локальных решений внутри подов. [1] (https://kubernetes.recipes/recipes/networking/kubernetes-rate-limiting-gateway-api/)
Поскольку в Kubernetes микросервисы масштабируются горизонтально (работают в десятках подов), обычный счетчик в памяти одного пода не подходит — лимит будет «сбрасываться» или умножаться на число реплик. Redis выступает централизованным хранилищем состояния для всех подов. [1] (https://github.com/formbricks/formbricks/issues/5956), [2] (https://kubernetes.recipes/recipes/networking/kubernetes-rate-limiting-gateway-api/)

Архитектура работы

Схема строится на трех уровнях в зависимости от того, где именно вы применяете лимитирование:
1. На уровне API Gateway / Ingress (рекомендуемый подход)
	• Запросы от клиента попадают в точки входа: Envoy, NGINX Ingress, Traefik или Gateway API (например, через Envoy Rate Limit Service или встроенные модули).
	• Gateway перехватывает запрос и делает запрос в Redis (или в отдельный сервис лимитов, который в свою очередь общается с Redis).
	• Если лимит не исчерпан, запрос уходит в под с приложением. Если исчерпан — Gateway сразу возвращает HTTP-код 429 Too Many Requests. [1] (https://kubernetes.recipes/recipes/networking/kubernetes-rate-limiting-gateway-api/)
2. На уровне приложения (Sidecar или библиотека внутри кода)
	• Sidecar-контейнер: Рядом с вашим приложением в поде запускается отдельный сервис-лимитер (например, на базе Envoy или специального daemon-пода), который проверяет сессию/IP в Redis.
	• Библиотека внутри кода: Ваше приложение (на Node.js, Go, Java и др.) при получении запроса обращается к общему кластеру Redis (например, через библиотеки вроде Bucket4j, Express-rate-limit и т.д.). [1] (https://medium.com/@nikkkhilshinde/how-did-we-managed-to-rate-limit-external-api-calls-in-kubernetes-env-with-redis-d0606f05b6a8), [2] (https://github.com/formbricks/formbricks/issues/5956)

Основные алгоритмы в Redis

Для предотвращения race condition (состояния гонки), когда сотни подов одновременно читают и изменяют счетчик, операции в Redis выполняются атомарно — чаще всего через Lua-скрипты. [1] (https://blog.callr.tech/rate-limiting-for-distributed-systems-with-redis-and-lua/), [2] (https://github.com/formbricks/formbricks/issues/5956)
• Fixed Window (Фиксированное окно):
	• Создается ключ в Redis с TTL (временем жизни), например: rate_limit:user_123:2026-11-16T11:00.
	• Команда INCR увеличивает счетчик. Если число больше лимита — отказ. Ключ автоматически удаляется по истечении времени окна.
• Sliding Window (Скользящее окно / Sorted Sets):
	• Использует структуры данных Redis ZSET (сортированные множества), где score — это таймстемп запроса.
	• Скрипт очищает старые записи (ZREMRANGEBYSCORE), считает количество элементов (ZCARD) и решает, пропускать ли новый запрос. Обеспечивает высокую точность. [1] (https://habr.com/ru/articles/916226/), [2] (https://blog.callr.tech/rate-limiting-for-distributed-systems-with-redis-and-lua/)
• Token Bucket / Leaky Bucket (Ведро токенов):
	• В Redis хранятся данные о количестве доступных токенов и времени последнего обновления. Приходящий запрос забирает токен; фоновый или ленивый пересчет по формуле времени наполняет ведро. [1] (https://medium.com/@nikkkhilshinde/how-did-we-managed-to-rate-limit-external-api-calls-in-kubernetes-env-with-redis-d0606f05b6a8), [2] (https://blog.callr.tech/rate-limiting-for-distributed-systems-with-redis-and-lua/)

Важные нюансы при эксплуатации в K8s

• Отказоустойчивость (Fail-open vs Fail-closed):
Что делать, если Redis в кластере Kubernetes упал или недоступен по сети?
	• Fail-open — пропускать трафик (лучше перегрузить бэкенд, чем положить сервис полностью).
	• Fail-closed — блокировать запросы (если критично защитить систему от DDoS).
• Сетевые задержки (Latency):
Каждый запрос к Redis добавляет несколько миллиaсекунд к времени ответа (RTT). В высоконагруженных системах Redis размещают в той же зоне доступности (Availability Zone) или используют локальное кэширование с асинхронной синхронизацией.
• Выбор ключа (Key Schema):
Ключи должны быть уникальными и не вызывать разрастания памяти в Redis (Cardinality explosion). Лимитируют обычно по:
	• IP-адресу (X-Forwarded-For)
	• JWT / API Key
	• ID пользователя [1] (https://opensource.zalando.com/skipper/tutorials/ratelimit/), [2] (https://kubernetes.recipes/recipes/networking/kubernetes-rate-limiting-gateway-api/), [3] (https://fastfox.pro/blog/tutorials/redis-lua-api-limiter/)

Разбор трех патчей


Патч 1: applyTo: CLUSTER (Куда отправлять запросы на проверку)

В терминологии Envoy Cluster — это не кластер Kubernetes, а группа апстрим-серверов (внешний сервис), куда Envoy может отправлять трафик. По умолчанию Envoy знает только о ваших сервисах из Istio, поэтому мы «знакомим» его с сервисом лимитов.
• operation: ADD: Добавить новый кластер в список известных.
• name: rate_limit_cluster: Внутреннее имя этого сервиса для самого Envoy.
• type: STRICT_DNS: Говорит Envoy периодически опрашивать DNS Kubernetes, чтобы узнать IP-адреса подов сервиса ratelimit.
• http2_protocol_options: {}: Обязательная настройка. Сервис лимитов общается по протоколу gRPC, который работает строго поверх HTTP/2.
• load_assignment: Указывает точный адрес сервиса в Kubernetes (ratelimit.default.svc.cluster.local на порту 8081).

Патч 2: applyTo: HTTP_FILTER (Как перехватывать запросы)

Каждый HTTP-запрос внутри Envoy проходит через цепочку фильтров (как FilterChain в Spring Security). Этот патч добавляет в цепочку новый фильтр, который ставит запрос «на паузу» и спрашивает разрешение у rate_limit_cluster.
• operation: INSERT_FIRST: Вставляет фильтр в самое начало цепочки, чтобы отсекать лишние запросы как можно раньше.
• name: envoy.filters.http.ratelimit: Имя встроенного в Envoy плагина для работы с внешним сервисом лимитов.
• domain: tasks-app: Пространство имен (контекст) для правил. В конфиге самого сервиса ratelimit (обычно это YAML-файл с правилами для Redis) правила должны быть описаны именно под доменом tasks-app.
• failure_mode_deny: false: Режим Fail-open. Если сервис ratelimit или Redis упадут, Envoy не будет блокировать пользователей, а пропустит запросы напрямую в Spring Boot. Если поставить true, при падении Redis весь сайт начнет отдавать ошибку 500.
• cluster_name: rate_limit_cluster: Ссылка на кластер, созданный в первом патче.

Патч 3: applyTo: VIRTUAL_HOST (Какие данные отправлять для подсчета)

В терминологии Envoy Virtual Host — это конфигурация конкретного домена и порта (например, example.com:80 или в вашем случае все хосты на порту 80 — *:80). Здесь мы настраиваем, какие именно характеристики запроса Envoy должен вытащить и передать в сервис лимитов в виде дескрипторов (ключей для Redis).
• operation: MERGE: Объединить (дописать) наши правила к уже существующим настройкам этого виртуального хоста.
• rate_limits и actions: Описывают, что именно мы хотим лимитировать. В вашем коде настроены два независимых правила:
	1. remote_address: {}: Envoy возьмет IP-адрес клиента и отправит его в сервис лимитов под ключом remote_address. В Redis создастся счетчик для каждого отдельного IP.
	2. generic_key (descriptor_value: global): Envoy отправит статическую строку generic_key: global. Это нужно для создания общего лимита на все приложение (например, не более 1000 запросов в секунду от всех пользователей суммарно).

Как это работает вместе при запросе

1. Клиент отправляет HTTP-запрос на ваш Istio Ingress Gateway (порт 80).
2. Срабатывает фильтр из Патча 2.
3. По правилам Патча 3 Envoy формирует gRPC-сообщение: «Домен tasks-app, IP клиента 1.2.3.4, ключ global. Можно пропустить?».
4. Envoy отправляет это сообщение по адресу из Патча 1 (ratelimit.default.svc.cluster.local:8081).
5. Сервис ratelimit проверяет счетчики в Redis и отвечает Envoy (OK или OVER_LIMIT).
6. Если OK — запрос летит дальше в ваш Spring Boot. Если OVER_LIMIT — Envoy сам возвращает клиенту 429 Too Many Requests, и Spring Boot даже не узнает об этом запросе.

Понимание архитектуры здесь очень простое — вы путаете Istio Ingress Gateway и Envoy, думая, что это две разные программы. На самом деле это одно и то же.

1. Кто такой Istio Ingress Gateway и где там Envoy?

Istio Ingress Gateway — это и есть обычный под с запущенным внутри прокси-сервером Envoy.
В Istio вообще нет своего прокси-сервера: вся сетка Istio (и шлюзы, и сайдкары рядом с микросервисами) построена поверх Envoy. Istio выступает лишь как «мозг» (Control Plane), который переводит ваши красивые YAML-манифесты (Gateway, VirtualService, EnvoyFilter) в огромный конфиг-файл и скармливает его процессу Envoy.
Как на самом деле выглядит путь запроса:
text
[Клиент] 
   │ (HTTP-запрос)
   ▼
[Istio Ingress Gateway (это и есть Envoy)]  ◄── Ваша граница кластера
   │  1. Перехватывает запрос (наш Патч 2)
   │  2. Спрашивает по gRPC: "Можно пустить?" ──► [Сервис ratelimit] ──► [Redis]
   │  3. Получает ответ: "Да" (или отдает 429)
   ▼
[Ваш под со Spring Boot]
Используйте код с осторожностью.
• Сервис ratelimit + Redis не стоят «на пути» трафика как прокси. Они стоят в стороне. Envoy просто «звонит» им по внутренней сети кластера, спрашивает разрешение и, получив ответ, сам решает: пропустить запрос в Spring Boot или сбросить его с ошибкой 429.

2. Почему под ratelimit сейчас запущен как 3/3?

В вашем манифесте ratelimit-deployment.yaml вы сами описали 2 контейнера, а Istio автоматически добавил 3-й:
1. ratelimit — сам сервис подсчета лимитов (вы описали его первым в манифесте).
2. statsd-exporter — сборщик метрик для Prometheus (вы описали его вторым в манифесте).
3. istio-proxy — сайдкар-контейнер с Envoy, который Istio автоматически подселил в ваш под, потому что в неймспейсе default включена автоинъекция.

Чем это грозит и как исправить?

Из-за того, что в поде ratelimit сидит третий контейнер (istio-proxy), весь входящий трафик в этот под перехватывается им. В вашем EnvoyFilter (Патч 1) вы настроили подключение к ratelimit по обычному (нешифрованному) gRPC, а istio-proxy внутри пода ratelimit может требовать шифрование (mTLS) или ломать HTTP/2-соединение, если не настроены порты.
Чтобы не усложнять конфигурацию mTLS и сэкономить память в кластере, лучше отключить сайдкар Istio конкретно для пода ratelimit (и для redis, если он у вас 2/2).
Добавьте аннотацию sidecar.istio.io/inject: "false" в template.metadata.annotations вашего Deployment:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ratelimit
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      app: ratelimit
  template:
    metadata:
      labels:
        app: ratelimit
      annotations:
        sidecar.istio.io/inject: "false" # <-- Отключаем 3-й контейнер Istio
    spec:
      containers:
        - name: ratelimit
          # ... остальной ваш код
```

После применения этого изменения и удаления лишнего statsd-exporter ваш под станет 1/1 — чистым, легким и гарантированно принимающим gRPC-запросы от Ingress Gateway.

> погоди, можно еще раз, что такое патч?

Патч (patch) в переводе с английского означает «заплатка». В IT это точечное изменение, которое вносится в уже существующий текст, код или файл конфигурации без необходимости переписывать его целиком.
В вашем случае с Istio и Envoy это работает так:
1. Что делает Istio по умолчанию:
Istio сам автоматически генерирует для Envoy огромный, сложный конфигурационный файл (на тысячи строк), основываясь на ваших обычных манифестах (Gateway, VirtualService, Service). Вы этот файл руками не пишете и не храните.
2. Зачем нужен EnvoyFilter и патчи:
В стандартных настройках Istio нет кнопки «подключить внешний Redis Rate Limit». Чтобы добавить эту функцию, вам нужно залезть внутрь сгенерированного Istio конфига и дописать туда пару блоков.
Поскольку вы не можете просто открыть этот виртуальный файл в блокноте и отредактировать, вы пишете инструкцию для Istio (configPatches — «заплатки конфигурации»).
Каждый элемент в списке configPatches — это один шаг вашей инструкции, который состоит из трех команд:
• applyTo (Куда смотреть): В какой именно раздел огромного конфига Envoy нужно зайти (например, в список внешних серверов CLUSTER или в цепочку обработки запросов HTTP_FILTER).
• match (Что найти): По каким приметам найти нужное место внутри этого раздела (например, найти настройки, относящиеся только к GATEWAY и порту *:80).
• patch (Что сделать): Какое именно действие выполнить в найденном месте:
	• ADD — добавить новый блок в конец;
	• INSERT_FIRST — вставить новый блок в самое начало;
	• MERGE — дописать новые строчки внутрь уже существующего блока.
Простая аналогия:
Представьте, что Istio каждый раз заново печатает многостраничную книгу (конфиг Envoy). Вместо того чтобы переписывать всю книгу вручную, вы кладете сверху стикеры с пометками (патчи): «На странице 45 после второго абзаца вклей вот этот текст». Istio при сборке читает эти стикеры и сам вклеивает ваши куски в нужные места.
