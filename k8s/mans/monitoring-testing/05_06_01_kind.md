# Создание нового кластера на kind

> ну и ну.. ты сказал про kind..  я почитал и выяснил, что он легче minikube. думаю, мне стоит его использовать, раз minikube вызвал проблемы с ресурсами. получается, мне теперь надо все заново настраивать?

Переход с minikube на kind — это не «начинать всё заново», а **сменить только инфраструктурный слой**. Ваши манифесты приложений (Deployment, Service, ConfigMap, Secret) остаются практически без изменений. Основная работа — заново развернуть *кластер* и *инфраструктурные компоненты* (Istio, мониторинг), но не переписывать приложения.

### 🧐 Что переносится, а что нужно настраивать заново

**✅ Переносится без изменений (или с минимальными правками):**
*   **Манифесты приложений:** `Deployment` (tasks-service, gateway, postgres, kafka), `Service`, `ConfigMap`, `Secret`. Их логика и структура не зависят от того, minikube это или kind.
*   **Ваш код и Docker-образы:** Приложения собираются так же, как и раньше.
*   **Конфигурация приложений:** `application.yaml`, `config-repo` — всё остаётся.

**🔄 Нужно будет настроить заново (или адаптировать):**
*   **Сам кластер Kubernetes:** Вместо minikube вы создаёте кластер через `kind create cluster`.
*   **Загрузка образов:** В minikube вы использовали `minikube image load`. В kind образы нужно загружать иначе (например, через `kind load docker-image`), либо собирать их сразу внутри Docker-демона, который использует kind.
*   **Ingress / Доступ снаружи:** `minikube tunnel` больше не будет. В kind для доступа к сервисам типа `LoadBalancer` (например, Istio Ingress Gateway) потребуется установить **MetalLB** или использовать `port-forward`.
*   **Istio:** `istioctl install` нужно будет выполнить заново для нового кластера.
*   **Мониторинг (Prometheus, Grafana, Loki):** Helm-чарты (если вы их использовали) нужно будет установить заново. Для kind это стандартная практика.

### 📋 Пошаговый план перехода

1.  **Создайте кластер kind.**
    Установите kind (`brew install kind`) и создайте кластер. Для доступа к портам (например, для Istio Gateway) можно сразу указать проброс портов в конфиге:
    ```yaml
    # kind-config.yaml
    kind: Cluster
    apiVersion: kind.x-k8s.io/v1alpha4
    nodes:
    - role: control-plane
      extraPortMappings:
      - containerPort: 80
        hostPort: 80
      - containerPort: 443
        hostPort: 443
    ```
    ```bash
    kind create cluster --name tasks-cluster --config kind-config.yaml
    ```

2.  **Настройте доступ к сервисам (Ingress/LoadBalancer).**
    Для полноценной работы Istio Ingress Gateway установите **MetalLB**, который умеет выдавать внешние IP для сервисов типа `LoadBalancer` в kind.

3.  **Разверните приложения.**
    Примените ваши существующие манифесты (`kubectl apply -f ...`) для tasks-service, gateway и баз данных. Единственное, что нужно будет проверить — как вы загружаете образы. Если не хотите возиться с `kind load`, можно настроить локальный Docker-реестр, но для учебного проекта проще всего использовать `kind load docker-image myorg/tasks-service:1.0`.

4.  **Установите Istio и мониторинг.**
    Выполните `istioctl install` и установите Helm-чарты для Prometheus, Grafana, Loki так же, как делали это раньше.

### 💎 Итог

Вы не теряете результаты своей работы. Ваш **код, конфигурации и манифесты приложений** — это 80% ценности. Переезд на kind — это в основном **пересборка инфраструктурного окружения** (сам кластер, Istio, мониторинг) и настройка доступа к нему. Kind действительно легче и ближе к CI/CD-практикам, так что для дальнейших экспериментов с нагрузочным тестированием это хороший выбор.


> а у меня же роль gateway выполняет приложение spring cloud gateway, или нет?

Отличный вопрос — и в нём есть **тонкость**, которая многих путает. Короткий ответ: **оба выполняют роль gateway, но на разных уровнях**. Spring Cloud Gateway **не заменяет** Istio Ingress Gateway — они **работают вместе**, но решают разные задачи.

## 🗺️ Два gateway в вашей архитектуре

В вашей исходной схеме (когда был Kubernetes + Istio) было **два** gateway:

```
Клиент → [Istio Ingress Gateway] → [Spring Cloud Gateway] → tasks-service
         ↑                        ↑
         инфраструктурный          прикладной
         (Envoy)                   (Java)
```

| | **Istio Ingress Gateway** | **Spring Cloud Gateway** |
|---|---|---|
| **Что это** | Envoy-прокси в namespace `istio-system` | Java-приложение (WebFlux) |
| **Уровень** | Инфраструктурный (L4–L7) | Прикладной (L7) |
| **Точка входа в кластер** | ✅ **Да** — принимает трафик снаружи | ❌ Нет — работает **внутри** кластера |
| **mTLS между сервисами** | ✅ Да | ❌ Нет |
| **Маршрутизация по пути** | ✅ Да (грубая, через `VirtualService`) | ✅ Да (гибкая, с фильтрами) |
| **Circuit breaker / rate limit** | ✅ Да (через Istio) | ✅ Да (через Resilience4j) |
| **Аутентификация JWT** | ✅ Да (RequestAuthentication) | ✅ Да (Spring Security) |
| **Фильтры, rewrite, headers** | ⚠️ Ограниченно | ✅ Полноценно |

## 🤔 Зачем **два** gateway?

Логичный вопрос: «Если Istio умеет маршрутизировать, зачем ещё Spring Cloud Gateway?» Причины:

### 1. **Разделение ответственности**

- **Istio Ingress** — «пропустить трафик в кластер, обеспечить mTLS, применить базовые политики».
- **Spring Cloud Gateway** — «применить бизнес-логику на входе: аутентификация, rate limit по пользователю, обогащение headers, трансформация, агрегация».

### 2. **Гибкость прикладного слоя**

Spring Cloud Gateway **легче менять** — это Java-код. Добавить фильтр, изменить логику маршрута, интегрировать с Keycloak — **проще**, чем писать EnvoyFilter.

### 3. **Istio не всегда нужен**

**В учебном проекте** вы **можете обойтись без Istio Ingress** — использовать **только** Spring Cloud Gateway как точку входа (через `Service type=LoadBalancer` или `NodePort`). Но тогда вы **теряете**:
- mTLS между сервисами.
- Circuit breaker на уровне сети (DestinationRule).
- Rate limit на уровне Envoy.
- Метрики трафика «из коробки».

## 🎯 Что это значит для вашего текущего эксперимента

Вы сейчас **не в Kubernetes**. У вас **локально**:
- `tasks-service` — на порту 8091.
- `spring-cloud-gateway` — на порту 8080 (когда запускаете).

**Istio Ingress Gateway здесь нет** — и **не нужен**. Ваш эксперимент «с Gateway и без Gateway» — это **чистый** замер **прикладного** gateway. Это **правильно** для слоя 2.

**Когда перейдёте на kind и добавите Istio** — у вас снова будет **два** gateway:
```
k6 → [Istio Ingress] → [Spring Cloud Gateway] → tasks-service
```

Тогда вы **измерите дельту** от **каждого**:
- «Без Gateway: p(95) = 8ms».
- «+ Spring Cloud Gateway: p(95) = 15ms → **+7ms**».
- «+ Istio Ingress: p(95) = 18ms → **+3ms** от Istio».

**Каждый слой — точная цифра.** Это и есть **инкрементальный подход**.

## ⚠️ Важное уточнение про «роль gateway»

**Если вы имеете в виду** «кто принимает трафик **снаружи** кластера» — это **Istio Ingress Gateway** (или `Service type=LoadBalancer`). Spring Cloud Gateway **внутри** кластера, он **не доступен** снаружи напрямую (если не сделать его `LoadBalancer`).

**Если вы имеете в виду** «кто маршрутизирует запросы к сервисам» — **оба**. Istio — на уровне сети (по путям, хостам), Spring Cloud Gateway — на уровне приложения (с фильтрами).

**Если вы имеете в виду** «кто применяет бизнес-логику на входе» — **Spring Cloud Gateway**. Istio — инфраструктурный, не «бизнесовый».

Вот пошаговый план, как развернуть полноценный кластер в `kind` и подготовить его к нагрузочному тестированию.

### 🗺️ Шаг 1: Создание кластера с пробросом портов

Чтобы в будущем получить доступ к вашему `gateway` (или Istio Ingress) снаружи, `kind` нужно сразу создать с пробросом портов.

1.  **Создайте файл `kind-config.yaml`**:
    ```yaml
    kind: Cluster
    apiVersion: kind.x-k8s.io/v1alpha4
    name: tasks-cluster
    nodes:
    - role: control-plane
      extraPortMappings:
      - containerPort: 80
        hostPort: 80
      - containerPort: 443
        hostPort: 443
    ```
    *   `extraPortMappings` говорит Docker'у пробросить порты 80 и 443 с вашего Mac внутрь узла кластера.

2.  **Создайте кластер**:
    ```bash
    kind create cluster --config kind-config.yaml
    ```
    Проверьте, что кластер работает:
    ```bash
    kubectl cluster-info
    kubectl get nodes
    ```

### ⚖️ Шаг 2: Установка MetalLB (эмуляция LoadBalancer)

Для сервисов типа `LoadBalancer` (например, для Istio Ingress Gateway) в `kind` нужен **MetalLB**. Он будет выдавать внешний IP-адрес.

1.  **Установите MetalLB**:
    ```bash
    kubectl apply -f https://raw.githubusercontent.com/metallb/metallb/v0.14.9/config/manifests/metallb-native.yaml
    ```
    Дождитесь, пока его поды будут готовы.

2.  **Определите подсеть Docker-сети `kind`**:
    ```bash
    docker network inspect kind
    ```
    В выводе найдите поле `"Subnet"` (например, `"Subnet": "192.168.97.0/24"`).

3.  **Создайте пул IP-адресов для MetalLB**. Замените `192.168.97.100-192.168.97.110` на диапазон из вашей подсети (например, последние 10 адресов):
    ```bash
    kubectl apply -f - <<EOF
    apiVersion: metallb.io/v1beta1
    kind: IPAddressPool
    metadata:
      name: kind-pool
      namespace: metallb-system
    spec:
      addresses:
      - 192.168.97.100-192.168.97.110
    ---
    apiVersion: metallb.io/v1beta1
    kind: L2Advertisement
    metadata:
      name: kind-l2
      namespace: metallb-system
    spec:
      ipAddressPools:
      - kind-pool
    EOF
    ```
    Теперь сервисы `LoadBalancer` будут получать IP из этого пула.

### 🐳 Шаг 3: Загрузка Docker-образов в кластер

`kind` использует собственное хранилище образов, поэтому ваши локальные Docker-образы ему не видны. Их нужно загрузить явно.

1.  **Соберите образы** (как обычно):
    ```bash
    docker build -t myorg/tasks-service:1.0 .
    docker build -t myorg/spring-cloud-gateway:1.0 .
    ```

2.  **Загрузите их в `kind`**:
    ```bash
    kind load docker-image myorg/tasks-service:1.0 --name tasks-cluster
    kind load docker-image myorg/spring-cloud-gateway:1.0 --name tasks-cluster
    ```

3.  **Важно**: В ваших манифестах `Deployment` для контейнеров `tasks-service` и `gateway` установите:
    ```yaml
    imagePullPolicy: IfNotPresent
    ```
    (или `Never`), чтобы Kubernetes не пытался скачивать их из Docker Hub.

## 🔄 Что нужно изменить (3 пункта)

### 1. `imagePullPolicy` — с `Never` на `IfNotPresent`

В minikube вы использовали `imagePullPolicy: Never` — потому что образы загружались через `minikube image load`. В kind — то же самое, но **лучше** `IfNotPresent`:

```yaml
# Было в minikube
imagePullPolicy: Never

# Стало в kind (тоже работает)
imagePullPolicy: IfNotPresent
```

**Почему:** `Never` — жёстко, если образа нет, под **не запустится**. `IfNotPresent` — если образа нет, попробует скачать из Docker Hub (что полезно, если забыли `kind load`).

### 2. Загрузка образов — `kind load docker-image`

```bash
# Было в minikube
minikube image load myorg/tasks-service:1.0

# Стало в kind
kind load docker-image myorg/tasks-service:1.0 --name tasks-cluster
```

**Ничего в манифестах не меняется** — просто другой инструмент для загрузки образов.

### 3. Доступ снаружи — `kubectl port-forward` или MetalLB

**В minikube** вы использовали `minikube tunnel` для `LoadBalancer`-сервисов и `minikube service` для доступа.

**В kind** — два варианта:

| Вариант | Как | Когда использовать |
|---|---|---|
| **`kubectl port-forward`** | `kubectl port-forward svc/tasks-service 8091:80` | **Проще всего**, для тестов |
| **MetalLB** | Даёт внешний IP сервисам `LoadBalancer` | Для Istio Ingress Gateway, production-like |

**Рекомендую `kubectl port-forward`** для начала — это **проще**, и работает без дополнительной настройки. Для Istio Ingress Gateway позже поставите MetalLB.

## ⚠️ Что нужно **проверить** (не изменить, а именно проверить)

### 1. Connection strings — с `localhost` на имя Service

Если в вашем локальном эксперименте (Docker + IDE) вы использовали `localhost:5432`, а теперь запускаете PostgreSQL **внутри kind** — строка подключения **должна быть**:

```yaml
# ❌ Было (Docker на хосте)
spring.datasource.url=jdbc:postgresql://localhost:5432/tasksdb

# ✅ Стало (PostgreSQL в kind)
spring.datasource.url=jdbc:postgresql://postgres:5432/tasksdb
#                                           ^^^^^^^^
#                                     имя Kubernetes Service
```

То же для MongoDB, Kafka, config-server — все ссылки **на имена Service**, а не на `localhost`.

### 2. Namespace — всё в `default`

Убедитесь, что **все** манифесты — в `default` (или везде одинаковый namespace). Если `postgres` в `default`, а `tasks-service` в `default` — всё резолвится. Если в разных — нужно полное DNS-имя: `postgres.default.svc.cluster.local`.

### 3. `config-repo` — URL Config Server

Если у вас был Spring Cloud Config — URL `http://config-server:8888` **не меняется**. Config Server живёт в kind так же, как в minikube.

## 💡 Бонус: k6 как Job внутри kind — **лучше**, чем port-forward

В kind у вас есть **огромное преимущество** перед локальным экспериментом: вы можете запустить **k6 как Job внутри кластера**. Это **убирает** `port-forward` из уравнения (ту самую проблему, с которой вы столкнулись).

**`k6-job.yaml`:**
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: k6-loadtest
spec:
  template:
    spec:
      containers:
        - name: k6
          image: grafana/k6:latest
          command: ["k6", "run", "/scripts/script.js"]
          volumeMounts:
            - name: script
              mountPath: /scripts
      restartPolicy: Never
      volumes:
        - name: script
          configMap:
            name: k6-script
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: k6-script
data:
  script.js: |
    import http from 'k6/http';
    import { check, sleep } from 'k6';

    export const options = {
      stages: [
        { duration: '30s', target: 100 },
        { duration: '30s', target: 500 },
        { duration: '30s', target: 1000 },
        { duration: '30s', target: 0 },
      ],
    };

    export default function () {
      const res = http.post('http://tasks-service/tasks/create',
        JSON.stringify({ title: `task-${__VU}-${__ITER}` }),
        { headers: { 'Content-Type': 'application/json' } });
      check(res, { 'status is 201': (r) => r.status === 201 });
      sleep(1);
    }
```

```bash
kubectl apply -f k6-job.yaml
kubectl logs -f job/k6-loadtest
```

**Преимущества:**
- Нет `port-forward` → нет «узкого места» туннеля.
- k6 **внутри** кластера → `tasks-service` резолвится по имени.
- Результаты **чистые** — вы измеряете **только** сервис, без overhead клиента.
