### 🎯 Нужен ли вам Ingress Gateway?

В вашей текущей схеме роль «входной точки» уже выполняет **Spring Cloud Gateway**. Однако **Istio Ingress Gateway** — это компонент **другого уровня**. Он работает на уровне инфраструктуры (L4-L7) и является **единой точкой входа в service mesh** для всего внешнего трафика.

Если вы хотите протестировать **полный стек** так, как он работал бы в production (внешний трафик → Istio Ingress → Spring Cloud Gateway → tasks-service), то **Istio Ingress Gateway вам необходим**. Он позволит вам измерить накладные расходы именно этого слоя и увидеть, как mesh управляет входящим трафиком.

### ⚠️ Важный момент: профиль `minimal`

Вы правы: профиль `minimal` устанавливает **только control plane (`istiod`)**. Он **не включает** в себя `istio-ingressgateway` и `istio-egressgateway`. Это сделано для того, чтобы вы могли управлять data plane (шлюзами) отдельно.

Поэтому, если вы установите Istio с профилем `minimal`, у вас не будет Ingress Gateway. Чтобы его добавить, у вас есть два пути:

1. **Установить его отдельно** после установки `minimal` (например, через `istioctl` с указанием манифеста для gateway).
2. **Использовать профиль `default`** (или `demo`), который устанавливает и control plane, и Ingress Gateway «из коробки».

### 💡 Рекомендация для вашего учебного проекта

Учитывая, что вы хотите измерить накладные расходы каждого слоя и у вас ограничены ресурсы (kind на ноутбуке), я бы рекомендовал **профиль `default`**. Он даст вам готовый Istio Ingress Gateway, и вы сможете сосредоточиться на тестировании, а не на ручной сборке компонентов.

Установка будет выглядеть так:
```bash
istioctl install --set profile=default -y
```

После этого у вас появится под `istio-ingressgateway`, и вы сможете направить на него трафик от k6, а он уже будет перенаправлять его на ваш Spring Cloud Gateway.

Все три манифеста — это не дублирование, а **разные слои управления трафиком**, и в вашей текущей архитектуре они нужны, если вы хотите получить полноценный входной узел Istio. Давайте разберём каждый.

### 🚪 1. `Gateway` — это «дверь» в ваш service mesh

`Gateway` — это манифест, который **не создаёт поды**. Он говорит уже существующему поду `istio-ingressgateway` (который вы устанавливаете отдельно) следующее: «Слушай порт 80 и принимай HTTP-трафик на любые хосты». Без этого манифеста ваш Ingress Gateway будет работать, но **не будет знать, куда и на каком порту смотреть** за входящим трафиком.

**Когда он нужен:** Всегда, если вы хотите принимать трафик снаружи через Istio. Если вы решите вообще не использовать Istio Ingress Gateway (например, оставить Spring Cloud Gateway точкой входа), то этот манифест не нужен.

### 🗺️ 2. `VirtualService` — это «карта маршрутов» внутри mesh

`VirtualService` — это **правила маршрутизации**. Он привязывается к `Gateway` и говорит: «Трафик, который пришёл на этот Gateway, направляй в сервис `spring-cloud-gateway` на порт 80». Без него `Gateway` просто примет соединение, но **не будет знать, что с ним делать дальше**.

**Когда он нужен:** Всегда, если вы хотите, чтобы трафик от Istio Ingress Gateway доходил до вашего приложения. Это ключевой манифест для маршрутизации.

### 🔒 3. `PeerAuthentication` — это «политика безопасности» (mTLS)

`PeerAuthentication` — это **не маршрутизация**, а **безопасность**. Он определяет, как поды в вашем namespace (или весь mesh) должны общаться друг с другом: по шифрованному каналу (mTLS) или обычному HTTP.

В вашем манифесте указан режим `PERMISSIVE`. Это означает: «Разрешаю принимать как шифрованный (mTLS), так и обычный (plaintext) трафик». Этот режим **крайне полезен на этапе миграции** или в учебном проекте, потому что он **не ломает** существующие соединения, если какие-то компоненты ещё не имеют sidecar-прокси.

**Когда он нужен:** Если вы **не тестируете безопасность** и не хотите, чтобы mTLS мешал вашему нагрузочному тестированию, этот манифест **можно не применять**. По умолчанию Istio и так работает в режиме `PERMISSIVE`, если явно не задан `STRICT`. Однако, если вы хотите **явно зафиксировать** это поведение и показать в резюме, что умеете управлять политиками безопасности, — оставьте его.

### 🎯 Итог: что из этого обязательно?

| Манифест | Роль | Нужен для нагрузочного теста? |
|---|---|---|
| **`Gateway`** | Открывает порт на Ingress Gateway | ✅ **Да**, если хотите принимать трафик снаружи |
| **`VirtualService`** | Направляет трафик от Gateway в ваш сервис | ✅ **Да**, иначе трафик «потеряется» |
| **`PeerAuthentication`** | Управляет mTLS (шифрованием) | ⚠️ **Опционально**, но полезно для учебного проекта (режим `PERMISSIVE` безопасен) |

**Важное напоминание:** Если вы устанавливаете Istio с профилем `minimal`, встроенного пода `istio-ingressgateway` **не будет**. Вам нужно будет либо установить его отдельно (`istioctl install --set profile=minimal --set components.ingressGateways[0].enabled=true`), либо использовать профиль `default`. Без пода `istio-ingressgateway` манифест `Gateway` будет бесполезен, потому что ему не к чему привязаться.

Таким образом, для полноценного тестирования слоя Istio вам нужны **все три манифеста**, но `PeerAuthentication` можно оставить «на потом», если вы хотите сначала сосредоточиться только на маршрутизации и производительности.


> установив istio и применив все его деплойменты - к моим spring cloud gateway и tasks-service - добавятся envoy sidecar ?

Да,Envoy sidecar добавятся, но не автоматически после простой установки Istio и применения ваших манифестов. Для этого нужно выполнить два обязательных условия. Разберём их, а также один важный нюанс, который напрямую повлияет на ваши будущие нагрузочные тесты.

### 🔑 Условие первое: Метка на namespace

Istio не внедряет sidecar в каждый под кластера по умолчанию. Автоматическое внедрение (automatic injection) работает через **вебхук**, который срабатывает только для подов, создаваемых в namespace с определённой меткой.

Вам нужно пометить namespace, где живут ваши приложения (скорее всего, `default`), чтобы Istio знал, что сюда нужно добавлять sidecar:

```bash
kubectl label namespace default istio-injection=enabled --overwrite
```

Без этой метки поды `tasks-service` и `spring-cloud-gateway` будут создаваться **без** контейнера `istio-proxy`.

### 🔄 Условие второе: Пересоздание подов

Вебхук срабатывает **только в момент создания пода**. Если вы пометили namespace, но поды уже были запущены раньше, они **не получат** sidecar «на лету». Их нужно пересоздать:

```bash
kubectl rollout restart deployment/tasks-service
kubectl rollout restart deployment/spring-cloud-gateway
```

После этого в подах появятся **два контейнера** (ваше приложение + `istio-proxy`), и в колонке `READY` будет `2/2`. Это и будет означать, что sidecar успешно внедрены.

### ⚠️ Важный нюанс: Профиль `minimal` и Ingress Gateway

Вы упомянули, что читали про профиль `minimal`. Это критически важный момент для вашей архитектуры.

Профиль `minimal` устанавливает **только control plane (`istiod`)** и **не включает** `istio-ingressgateway`. Это означает, что если вы установите Istio с этим профилем, ваши манифесты `Gateway` и `VirtualService` **не заработают**, потому что им не к чему будет привязаться — самого пода шлюза не будет существовать.

Для полноценного тестирования слоя Istio с внешней точкой входа вам нужен профиль, который устанавливает Ingress Gateway. Самый простой путь — использовать профиль `default`:

```bash
istioctl install --set profile=default -y
```

Это установит и `istiod`, и `istio-ingressgateway`, и тогда ваши `Gateway`/`VirtualService` манифесты применятся корректно.

## 🎯 Три ключевых вывода

### 1. **Overhead Istio в «чистой зоне» = +11.5ms**

При 900 VU (без насыщения):
- **p(95)**: 6.22 → 17.73ms (**+11.5ms**)
- **med**: 1.86 → 3.87ms (**+2ms**)
- **RPS**: 560 → 558 (**не изменился**)

**RPS не изменился** — Istio **не режет** throughput. Но каждый запрос стал **медленнее** на 11.5ms (p95) или 2ms (med). Это **стоимость** нескольких Envoy-hop'ов.

**Почему med выросла всего на 2ms, а p(95) — на 11.5ms?** Потому что в «хвосте» распределения (p95) скапливаются запросы, которые проходят через **все** hop'ы: Ingress Envoy → Gateway sidecar → Gateway Java → Gateway outbound Envoy → tasks-service sidecar → tasks-service Java. Каждый hop добавляет **немного**, но в сумме — **11ms**.

### 2. **Точка деградации сместилась влево**

| | Без Istio | С Istio |
|---|---|---|
| «Чистая зона» | до 900 VU (p95 < 10ms) | до **~900 VU** (p95 = 17.73ms) |
| Начало деградации | ~1000 VU | **~1000 VU** (p95 = 29.25ms) |
| Явная деградация | 1250 VU (p95 = 91.72ms) | **1250 VU** (p95 = 144.05ms) |
| Потолок RPS | ~1000 | **~1000** |

**Важно:** «потолок RPS» **не изменился** (~1000). Istio **не уменьшил** пропускную способность, но **сдвинул** границу «комфортной» latency. При 900 VU без Istio p(95) = 6ms (отлично), с Istio — 17ms (**приемлемо**, но **не идеально**).

### 3. **Дельта растёт при насыщении — очередь умножается**

```
900 VU:  +11.5ms
1250 VU: +52ms    (×4.5)
2000 VU: +102ms   (×8.9)
```

**Почему?** При насыщении **каждый** Envoy-hop имеет **свою очередь**. Когда Gateway «упирается» в пул, **Ingress Envoy** тоже начинает **накапливать** запросы. Две очереди **складываются** — отсюда **экспоненциальный** рост дельты.

- **Настроить `concurrency`** Envoy под CPU.
