> как включить метрики потоков spring boot 4
Чтобы включить метрики потоков (Thread metrics) в Spring Boot, используются Spring Boot Actuator и Micrometer. Метрики потоков JVM (например, jvm.threads.live, jvm.threads.daemon, jvm.threads.peak) собираются автоматически по умолчанию, как только вы подключаете Actuator. [1] (https://blog.ycrash.io/exposing-jvm-metrics-over-actuator-in-spring-boot-4/), [2] (https://dev.to/devcorner/spring-boot-actuator-and-micrometer-monitoring-made-easy-430h), [3] (https://uptrace.dev/blog/spring-boot-microservices-monitoring)

Шаг 1. Добавление зависимости

В ваш pom.xml (Maven) или build.gradle (Gradle) добавьте стартер Actuator:
• Maven:
xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
Используйте код с осторожностью.
• Gradle:
groovy
implementation 'org.springframework.boot:spring-boot-starter-actuator'
Используйте код с осторожностью.

Шаг 2. Включение и экспонирование эндпоинтов

По умолчанию через веб (HTTP) из всех эндпоинтов доступны только health и info. Чтобы увидеть метрики через браузер или систему мониторинга (например, Prometheus), нужно настроить их в application.yml или application.properties. [1] (https://www.baeldung.com/spring-boot-actuators), [2] (https://uptrace.dev/blog/spring-boot-microservices-monitoring)
Пример для application.yml:
yaml
management:
  endpoints:
    web:
      exposure:
        include: 'metrics,threaddump,prometheus' # или '*' чтобы открыть всё
  endpoint:
    metrics:
      enabled: true
Используйте код с осторожностью.
• /actuator/metrics — список всех доступных метрик. Чтобы посмотреть конкретно метрику потоков, перейдите по адресу:
	• http://localhost:8080/actuator/metrics/jvm.threads.live
	• http://localhost:8080/actuator/metrics/jvm.threads.daemon
	• http://localhost:8080/actuator/metrics/jvm.threads.peak
• /actuator/threaddump — дает подробный снимок (thread dump) всех потоков в формате JSON. [1] (https://medium.com/@sarveshkhamkar321/spring-boot-actuator-your-applications-built-in-health-monitor-7b9692890ef4), [2] (https://docs.spring.io/spring-boot/api/rest/actuator/threaddump.html)

Основные стандартные метрики потоков в Micrometer / Actuator


Имя метрики	Описание
jvm.threads.live	Общее число живых потоков (daemon + non-daemon)
jvm.threads.daemon	Количество фоновых daemon-потоков
jvm.threads.peak	Пиковое значение живых потоков с момента запуска JVM
jvm.threads.states	Распределение потоков по состояниям (RUNNABLE, WAITING, BLOCKED и др.)

Почему это происходит?

Для сбора детальной статистики по пулу потоков (сколько сейчас занято, какой лимит и т. д.) Micrometer обращается к JMX-метрикам самого встроенного контейнера Tomcat. Начиная с определенных версий Spring Boot, инициализация встроенного MBeanRegistry в Tomcat отключена по умолчанию. Без этого флага Actuator возвращает дефолтное значение-заглушку -1.0. [1] (https://www.datadoghq.com/blog/tomcat-architecture-and-performance/), [2] (https://cubeapm.com/blog/tomcat-monitoring-jmx-metrics-thread-pools-request-tracking/)
После изменения настройки и перезапуска приложения выполните ваш запрос curl повторно. Вы увидите реальное количество потоков (например, 200.0 для max_threads по умолчанию). [1] (https://proselyte.net/tomcat-for-devs/), [2] (https://www.baeldung.com/java-web-thread-pool-config)

В чем проблема?

Когда вы включаете Виртуальные потоки (Virtual Threads / Project Loom) в Spring Boot, классический пул потоков Tomcat полностью отключается. [1] (https://medium.com/javarevisited/virtual-threads-in-spring-boot-4-what-actually-changes-for-your-code-9b490b57f400), [2] (https://lukasgrigis.dev/blog/spring-boot-virtual-threads/)
Вместо фиксированного пула (где есть max, min-spare и т.д.) Tomcat переходит на режим "один виртуальный поток на каждый запрос" (Virtual Thread Per Task Executor). Потоки больше не переиспользуются, они создаются JVM динамически на лету и уничтожаются после обработки запроса. [1] (https://spring.io/blog/2022/10/11/embracing-virtual-threads/), [2] (https://medium.com/javarevisited/virtual-threads-in-spring-boot-4-what-actually-changes-for-your-code-9b490b57f400), [3] (https://www.linkedin.com/posts/artyom-badoyan_java-springboot-softwarearchitecture-activity-7516044357863534592-KOxP)
Поскольку стандартного пула потоков Tomcat физически больше не существует в памяти, JMX-метрики вроде config_max_threads, current_threads и busy_threads навсегда застывают на отметке -1.0, так как опрашивать больше нечего. Ваши настройки server.tomcat.threads.max: 400 и min-spare: 20 в этот момент просто игнорируются фреймворком. [1] (https://www.linkedin.com/posts/artyom-badoyan_java-springboot-softwarearchitecture-activity-7516044357863534592-KOxP), [2] (https://github.com/spring-projects/spring-boot/issues/49391), [3] (https://medium.com/javarevisited/virtual-threads-in-spring-boot-4-what-actually-changes-for-your-code-9b490b57f400), [4] (https://lukasgrigis.dev/blog/spring-boot-virtual-threads/)

Как теперь мониторить нагрузку в k8s?

Если вы используете виртуальные потоки, старые дашборды Grafana для Tomcat становятся "слепыми". Чтобы понимать, справляется ли приложение с нагрузкой, вам нужно отслеживать другие метрики: [1] (https://www.linkedin.com/posts/artyom-badoyan_java-springboot-softwarearchitecture-activity-7516044357863534592-KOxP)

1. Мониторинг "Несущих" потоков (Carrier Threads)

Виртуальные потоки выполняются поверх обычных потоков операционной системы (ForkJoinPool). Отслеживайте общие потоки JVM, которые теперь выполняют всю работу:
• jvm_threads_live_threads — общее число потоков в JVM.
• jvm_threads_states_threads{state="runnable"} — сколько несущих потоков сейчас реально выполняют код. [1] (https://github.com/spring-projects/spring-boot/issues/49391)

2. Мониторинг лимита соединений Tomcat

При работе с виртуальными потоками узким горлышком для входящего трафика становится не количество потоков, а количество сетевых соединений (Connections). Мониторьте метрику: [1] (https://www.linkedin.com/posts/artyom-badoyan_java-springboot-softwarearchitecture-activity-7516044357863534592-KOxP)
• tomcat_connections_current_connections
• tomcat_connections_config_max_connections (по умолчанию лимит равен 8192) [1] (https://www.linkedin.com/posts/artyom-badoyan_java-springboot-softwarearchitecture-activity-7516044357863534592-KOxP), [2] (https://lukasgrigis.dev/blog/spring-boot-virtual-threads/)
Если вы упретесь в лимит соединений, Kubernetes-поды начнут копить очередь, что покажет метрика tomcat_connections_config_max_connections в связке с вашим accept-count: 200.

3. Мониторинг пула подключений к БД (HikariCP)

Это главная ловушка виртуальных потоков. Приложение может породить 10 000 виртуальных потоков для обработки 10 000 запросов, но если ваш пул базы данных равен всего 10 (maximum-pool-size: 10), все эти потоки встанут в очередь за коннектом к БД. Появятся таймауты.
Обязательно выведите на дашборд: [1] (https://www.linkedin.com/posts/artyom-badoyan_java-springboot-softwarearchitecture-activity-7516044357863534592-KOxP)
• hikaricp_connections_pending — сколько потоков ждут свободного подключения к базе.
• hikaricp_connections_active — сколько соединений сейчас занято. [1] (https://habr.com/ru/articles/1046239/)

Разбор параметров Tomcat (для классических потоков)

Если бы виртуальные потоки были выключены, эти параметры управляли бы поведением вашего приложения следующим образом:
1. threads.max: 400 — это потолок вашей одновременной обработки. Приложение может одновременно выполнять ровно 400 запросов. Если придет 401-й запрос, Tomcat не будет создавать для него поток.
2. threads.min-spare: 20 — это «горячий старт». При запуске приложения Tomcat сразу создает 20 потоков и держит их наготове, чтобы первые пользователи не ждали, пока поток создастся в ОС.
3. accept-count: 200 — это длина очереди на уровне операционной системы (TCP backlog).
	• Если у вас заняты все max: 400 потоков, новые запросы не отбрасываются сразу. Они встают в очередь внутри ОС.
	• Ваша очередь может вместить ровно 200 запросов.
	• Если в очереди уже лежит 200 запросов, а потоки всё еще заняты, то 601-й запрос упадет сразу с ошибкой Connection refused (в k6 это выглядит как dial tcp: connect: connection refused).

Что происходит, когда вы включаете virtual: enabled: true?

В этот момент правила игры полностью меняются:
• Параметры threads.max и threads.min-spare игнорируются и превращаются в тыкву.
• Если k6 присылает 1000 одновременных запросов (виртуальных пользователей / VU), Tomcat создаст под них 1000 виртуальных потоков. Для него это очень дешево (один такой поток занимает всего пару килобайт в памяти).
• accept-count: 200 всё еще работает, но вы до него, скорее всего, даже не дойдете, потому что Tomcat будет моментально поглощать все входящие запросы и плодить под них виртуальные потоки.

А теперь самое главное: Стыковка с HikariCP (Базой данных)

По умолчанию пул соединений HikariCP равен всего 10 соединениям (maximum-pool-size: 10).
Представьте картину во время вашего теста в k6:
1. k6 отправляет 1000 одновременных запросов.
2. Tomcat радостно создает 1000 виртуальных потоков. Все они начинают выполняться одновременно.
3. Каждому из 1000 потоков для работы нужно сходить в базу данных. Они все одновременно бегут к HikariCP и говорят: "Дай коннект!".
4. HikariCP отвечает: "У меня есть только 10 соединений. Вот вам первые 10 потоков, работайте. Остальные 990 — встаньте в очередь".

И вот тут начинается катастрофа (Thread Pinning и Pool Timeout):

• По умолчанию поток ждет коннект из пула ровно 30 секунд (connection-timeout: 30000ms).
• Если за 30 секунд первые потоки не освободят базу данных, остальные 990 потоков начнут отваливаться по таймауту. В логах вы увидите: Connection is not available, request timed out after 30000ms. Пользователи в k6 получат HTTP 500.
• Эффект "Pinning" (Привязывание потоков): В Java виртуальные потоки во время выполнения синхронизированных блоков (synchronized) или работы с native-кодом (что часто бывает в старых драйверах БД) могут «прилипать» к физическому потоку процессора (Carrier Thread). Если это происходит, блокируется весь физический поток, и ваше приложение в k6 начинает жутко тормозить на ровном месте, хотя CPU в k8s может быть загружен всего на 10%.

Давайте разберем по полочкам, почему так происходит и как ваш Bulkhead меняет правила игры, особенно в контексте виртуальных потоков.

В чем смысл разницы (400 потоков vs 50 коннектов к БД)?

В классическом приложении (без виртуальных потоков) Tomcat-поток берет на себя запрос и ведет его «от и до». Но запрос к серверу состоит не только из общения с Postgres. Время жизни потока делится на фазы:
1. I/O на входе: Tomcat принимает байты от пользователя, парсит JSON, валидирует данные. (База данных еще не нужна).
2. Бизнес-логика: Проверка прав, маппинг объектов, подсчет чего-либо в памяти. (База данных еще не нужна).
3. Запрос к БД: Поток запрашивает коннект у HikariCP, отправляет SQL в Postgres и ждет ответа от диска/сети. (Коннект занят).
4. Формирование ответа: База отдала данные, поток сериализует их в JSON, накладывает фильтры. (Коннект уже освободился и вернулся в пул).
5. I/O на выходе: Поток медленно отдаёт этот JSON клиенту обратно по сети. (База данных не нужна).
Из условных 100 миллисекунд, что тратит Tomcat на один запрос, база данных может быть нужна всего на 10 мс. Это значит, что один коннект к БД успевает обслужить несколько потоков Tomcat по очереди. Именно поэтому пула в 50 соединений зачастую хватает, чтобы прокормить 400 классических потоков.

А зачем тогда нужен Bulkhead(maxConcurrentCalls = 20)?

Когда один под упирается в свои физические или архитектурные границы (запросы начинают выполняться долго, копится очередь), наступает этап масштабирования. В мире Kubernetes и больших нагрузок это решается комплексно.
Вот как устроена стратегия обработки высоких нагрузок на практике:

1. Горизонтальное масштабирование (Horizontal Pod Autoscaling — HPA)

Поскольку вы запускаете приложение в k8s, это ваш главный инструмент. Вместо того чтобы пытаться впихнуть 1000 VU в один под, нагрузка размазывается по нескольким копиям приложения.
• Как это работает: Перед вашими подами стоит Service (лоад-балансер k8s). Если k6 отправляет 600 запросов, а один под комфортно переваривает только 200, k8s настраивают так, чтобы при достижении определенного порога (например, 70% CPU или по кастомной метрике Prometheus) он автоматически создавал еще 2–3 пода. Нагрузка делится: каждый под получает свои 200 запросов и работает без задержек.

2. Главная ловушка масштабирования: База данных — это бутылочное горлышко (Single Point of Failure)

Вы можете легко размножить поды приложения в k8s хоть до 50 штук. Но PostgreSQL у вас, скорее всего, одна (или один primary-узел на запись).
Вот математика катастрофы при горизонтальном масштабировании:
• 1 под приложения = hikari.maximum-pool-size: 30 (30 коннектов к Postgres).
• Вы отмасштабировали приложение до 10 подов в k8s.
• Теперь 10 подов вместе попытаются открыть 300 соединений к одной и той же базе данных Postgres!
Если в настройках самой Postgres (max_connections) лимит установлен, например, в 100 соединений, то половина ваших подов просто упадет при старте с ошибкой подключения к БД, а k6 зафиксирует шквал ошибок.

Как архитектурно обрабатывают действительно большие нагрузки?

Когда упираются в лимиты одной базы данных, применяют следующие паттерны:

А. Пуллеры соединений перед БД (PgBouncer)

В мире Postgres каждое новое соединение от HikariCP заставляет Postgres порождать отдельный тяжелый процесс в ОС Linux. Если соединений становится больше 100–200, Postgres начинает тратить больше сил на переключение контекста процессора, чем на саму работу.
• Решение: Между Spring Boot и Postgres ставят PgBouncer. Он агрегирует тысячи виртуальных соединений от приложений и превращает их, например, в 20 реальных жестких соединений до самого движка Postgres.

Б. Разделение чтения и записи (CQRS / Read Replicas)

Обычно 80% запросов в приложениях — это чтение (просмотр тасок, поиск, отчеты) и только 20% — запись (создание, удаление).
• Решение: Рядом с основной Postgres (Master) поднимают реплику (Replica), куда данные только дублируются. В Spring Boot настраивают два датасорса. Все тяжелые GET-запросы уходят на реплику, а мастер-база освобождается для быстрых транзакций на запись.

В. Асинхронность и очереди (Event-Driven)

Если k6 тестирует метод создания задачи, и этот метод делает сложную логику в БД, то синхронно (в режиме "запрос-ответ") держать пользователя у экрана долго.
• Решение: fallbackCreateTask или даже сам основной метод переписывают так: приложение принимает запрос, моментально бросает сообщение в брокер (Kafka / RabbitMQ) "Надо создать задачу" и сразу отвечает клиенту HTTP 202 Accepted ("Принято, делаем"). Поток освобождается за 2 миллисекунды. Специальные воркеры потом разбирают эту очередь из Kafka с той скоростью, с которой Postgres способна её переварить.

Г. Кэширование (Redis)

Если 150 VU постоянно запрашивают одни и те же данные из БД, их закрывают кэшем. Запрос до Postgres даже не доходит, разгружая пулы HikariCP.

> дело в том, что все эти проблемы как раз вылазят при включенных виртуальных потоках. без них я еще не тестировал. а какой тогда профит использования виртуальных потоков в Spring Boot?

Главный профит виртуальных потоков (Virtual Threads) заключается в колоссальной экономии оперативной памяти и CPU при обработке «阻塞» (блокирующих) операций, что позволяет одному серверу удерживать в десятки раз больше одновременных сетевых соединений [Loom].
То, с чем вы столкнулись при нагрузочном тестировании в k6 — это классический «шок» от того, что бутылочное горлышко моментально сместилось из памяти приложения на диск и базу данных.
Давайте разберем, в чем именно выигрыш виртуальных потоков и почему в вашем тесте это пока неочевидно.

Как работает классический поток (Platform Thread)

Каждый обычный поток в Java жестко привязан к потоку операционной системы (ОС) [Loom].
• Память: Один поток ОС «съедает» ровно 1 МБ памяти под свой стек по умолчанию.
• Лимит: Если вы выделите приложению 1 ГБ памяти, вы физически не сможете создать больше ~800–1000 потоков, иначе приложение упадет с OutOfMemoryError: unable to create new native thread.
• CPU: Когда 400 потоков Tomcat одновременно работают, процессор тратит кучу времени не на полезный код, а на переключение контекста (Context Switching) между потоками ОС [Loom].

Как работает виртуальный поток (Virtual Thread)

Виртуальные потоки живут внутри памяти JVM, а не в ОС [Loom].
• Память: Один виртуальный поток весит всего несколько килобайт (от 2 до 10 КБ) [Loom].
• Лимит: Вы можете запустить 100 000 или даже 1 000 000 виртуальных потоков на самом обычном ноутбуке.
• CPU: Когда виртуальный поток делает блокирующий вызов (например, ждет ответ от внешней системы), JVM аккуратно «снимает» его с процессора и ставит на его место другой виртуальный поток. Процессор загружен полезной работой на 100%, переключения контекста ОС минимальны [Loom].

В чем тогда профит для Spring Boot?

Виртуальные потоки раскрывают свою суперсилу в I/O-intensive приложениях (где много сетевого ожидания), а именно:
1. Микросервисы, которые ходят в другие микросервисы:
Если ваш tasks-service для выполнения одной задачи должен вызвать по HTTP три других сервиса (например, user-service, billing-service, notification-service).
	• Без виртуальных потоков: Обычный поток Tomcat будет сидеть и тупо ждать ответов по сети. 400 запросов пришло — все 400 потоков уснули, приложение больше не принимает новые запросы, хотя CPU загружен на 1%.
	• С виртуальными потоками: Потоки засыпают внутри JVM, освобождая физический процессор. Сервис может обрабатывать десятки тысяч таких запросов одновременно.
2. Асинхронные долгоживущие соединения:
Стриминг данных, WebSockets, Server-Sent Events (SSE). Раньше для удержания 10 000 открытых WebSocket-соединений вам нужны были огромные сервера (или сложный реактивный стек WebFlux). С виртуальными потоками вы можете держать 50 000 соединений на одном скромном поде в Kubernetes.
3. Отказ от сложного реактивного программирования (WebFlux/Project Reactor):
Раньше, чтобы добиться такой производительности, приходилось писать сложный, нечитаемый реактивный код (с mono, flux, flatMap). Виртуальные потоки позволяют писать обычный, простой код (String result = restTemplate.get(...)) и при этом получать реактивную скорость.

Почему в вашем тесте вы получили проблемы?

База данных (PostgreSQL) — это не просто сетевое ожидание. Это физический диск, который должен записать или прочитать данные, и это жесткие блокировки (locks) на уровне таблиц/строк.
• Без виртуальных потоков (классический Tomcat): Сам Tomcat со своим лимитом max: 400 работал как естественный ограничитель (дроссель). Он просто не пускал внутрь приложения слишком много трафика. База данных жила в комфортном режиме, потому что приложение физически не могло завалить её запросами.
• С виртуальными потоками: Вы убрали этот естественный барьер. Теперь k6 подает нагрузку, Tomcat моментально открывает сотни потоков, и вся эта лавина трафика неуправляемо бьет напрямую в базу данных. База данных не может работать быстрее диска, она начинает тормозить, выстраивается очередь, и время ответа (Latency) драматически растет.

Резюме

Виртуальные потоки не делают саму базу данных быстрее. Они делают ваше приложение способным переваривать гигантские объемы сетевых запросов.
Чтобы получить от них профит при работе с БД, вам нужно управлять этим шквалом: использовать пуллеры (PgBouncer), кэширование, или, как вы уже сделали, жестко лимитировать конкурентный доступ к базе через Bulkhead.
